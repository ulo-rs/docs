---
title: Juniper Integration
description: Use ulo-graphql-juniper to add a GraphQL endpoint powered by the juniper crate, with a strongly-typed context.
---

`ulo-graphql-juniper` integrates Ulo with the [Juniper](https://github.com/graphql-rust/juniper) GraphQL library. Unlike `ulo-graphql-async-graphql`, Juniper uses a concrete, user-defined context type — every resolver receives your context struct directly, giving you full compile-time type safety.

The module mounts one HTTP endpoint: POST for queries and mutations, GET for the playground. It serves no subscriptions — the schema's subscription root is part of the module's type, but nothing carries subscription operations over a WebSocket. [`ulo-graphql-async-graphql`](/docs/graphql/async-graphql#subscriptions) is the integration that does.

## Installation

```toml title="Cargo.toml"
[dependencies]
ulo = "0.2"
ulo-graphql-juniper = "0.1"
juniper = "0.16"
ulo-http-axum = "0.1"
tokio = { version = "1", features = ["full"] }
```

## 1. Define the context

Your context struct is what Juniper resolvers receive. It holds references to services or data they need:

```rust
use juniper::Context as JuniperContext;

pub struct AppContext {
    pub users_service: UsersService,
    pub db: DatabaseService,
}

impl JuniperContext for AppContext {}
```

## 2. Define the schema

```rust
use juniper::{graphql_object, EmptyMutation, EmptySubscription, RootNode};

pub struct QueryRoot;

#[graphql_object(context = AppContext)]
impl QueryRoot {
    fn users(context: &AppContext) -> Vec<String> {
        context.users_service.find_all_names()
    }

    fn user(context: &AppContext, id: i32) -> Option<String> {
        context.users_service.find_one_name(id as u32)
    }
}

pub type AppSchema = RootNode<
    'static,
    QueryRoot,
    EmptyMutation<AppContext>,
    EmptySubscription<AppContext>,
>;
```

## 3. Build the context

Implement `ContextBuilder` to populate the context for each request. The `build` method receives the incoming `RequestPart` so you can read headers (e.g. auth tokens) alongside the services the builder carries.

The builder is passed by value to `for_root` — it is not resolved through the DI container. Construct it, and the services it captures, when building the module:

```rust
use async_trait::async_trait;
use ulo::RequestPart;
use ulo_graphql_juniper::ContextBuilder;

pub struct AppContextBuilder {
    users_service: UsersService,
    db: DatabaseService,
}

impl AppContextBuilder {
    pub fn new(users_service: UsersService, db: DatabaseService) -> Self {
        Self { users_service, db }
    }
}

#[async_trait]
impl ContextBuilder for AppContextBuilder {
    type Context = AppContext;

    async fn build(&self, _req: &RequestPart) -> AppContext {
        AppContext {
            users_service: self.users_service.clone(),
            db: self.db.clone(),
        }
    }
}
```

When you don't need context data, use the built-in `DefaultContextBuilder` and `DefaultContext`:

```rust
use ulo_graphql_juniper::{GraphQLModule, DefaultContextBuilder, DefaultContext};

// DefaultContext implements juniper::Context and is the context type
// when using DefaultContextBuilder
```

## 4. Register the module

Module `imports` entries are expressions, so a helper function keeps the declaration readable:

```rust
use ulo_graphql_juniper::GraphQLModule;
use juniper::{EmptyMutation, EmptySubscription, RootNode};

fn graphql_module() -> GraphQLModule<
    QueryRoot,
    EmptyMutation<AppContext>,
    EmptySubscription<AppContext>,
    AppContextBuilder,
> {
    let schema = RootNode::new(QueryRoot, EmptyMutation::new(), EmptySubscription::new());
    let context_builder = AppContextBuilder::new(UsersService::new(), DatabaseService::new());
    GraphQLModule::for_root(schema, context_builder)
        .with_path("/api/graphql")
        .with_playground(true)   // disable in production
}

#[module(
    imports: [graphql_module(), UsersModule, DatabaseModule],
)]
pub struct AppModule;
```

## 5. Run the server

```rust
#[tokio::main]
async fn main() {
    let mut app = UloFactory::create(AppModule).await.unwrap();
    app.use_http_adapter(AxumAdapter::new(), ("127.0.0.1", 3000)).unwrap();
    app.start().await.unwrap();
}
```

## Mounting more than one schema

A `GraphQLModule`'s identity is its full type — the schema roots, the context builder and the scalar — plus the path and the playground flag. Two imports differing in any of those are two modules, which decides what happens when a graph holds more than one:

- The same schema at two paths mounts two endpoints, each with its own context builder.
- An identical import reached through two module paths is a diamond: one module, one endpoint.
- Two modules on one path is a duplicate route, and the adapter's own router is what rejects it: registration panics out of `app.bind()` rather than returning a `StartupError` — axum's message is `Overlapping method route`. Give each endpoint its own path.

Changing only the context builder does not merge two modules onto one path; it makes them distinct, so the third case is what you get.

## Injecting the service

`GraphQLModule` exports the executor behind the endpoint under the token `"GraphQLService"`. A module that imports the GraphQL module can inject it and run a document without going through HTTP:

```rust
use ulo_graphql_juniper::GraphQLService;

type AppGraphQL = GraphQLService<
    QueryRoot,
    EmptyMutation<AppContext>,
    EmptySubscription<AppContext>,
    AppContextBuilder,
>;

#[injectable]
pub struct ReportJob {
    #[inject("GraphQLService")]
    graphql: AppGraphQL,
}
```

The registration token is that string, so a bare `#[inject]` by type does not reach the service. Name it, and spell out the parameters of `GraphQLService<Query, Mutation, Subscription, Ctx>` — an alias keeps that to one place. The trailing scalar parameter defaults to `juniper::DefaultScalarValue`.

`execute(query, operation_name, variables, http_req)` builds the context from the `RequestPart` you hand it and answers a `serde_json::Value` holding `data` and any `errors`.

## Comparison with async-graphql

|             | `ulo-graphql-async-graphql`          | `ulo-graphql-juniper`              |
| ----------- | ----------------------------- | --------------------------- |
| Context     | `Data` (type-erased map)      | Concrete struct (your type) |
| Type safety | Runtime lookup                | Compile-time                |
| Flexibility | Easier to add more data later | Explicit, all-or-nothing    |
| Subscriptions | `graphql-transport-ws` over WebSocket | none |

If your team values explicit, compile-checked context and doesn't mind the boilerplate of a concrete context type, Juniper is the stronger choice. If you want to incrementally add services to the context without changing the context type, async-graphql's `Data` container is more flexible.
