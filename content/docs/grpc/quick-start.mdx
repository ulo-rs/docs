This walkthrough builds a single-method gRPC service backed by an injected provider. Dependencies are listed in the [overview](/docs/grpc#installation).

<Steps>

<Step>

### Define the contract

`proto/orders.proto`:

```protobuf
syntax = "proto3";
package toni_examples.orders;

service Orders {
    rpc Create (CreateOrderRequest) returns (CreateOrderResponse);
}

message CreateOrderRequest { string item = 1; uint32 qty = 2; }
message CreateOrderResponse { uint64 id = 1; string status = 2; }
```

</Step>

<Step>

### Compile it in build.rs

Two steps, in order. `tonic-prost-build` compiles the proto into messages and a service trait; `toni_build::shapes` then reads that trait and writes what each method carries beside it.

```rust title="build.rs"
fn main() -> Result<(), Box<dyn std::error::Error>> {
    tonic_prost_build::compile_protos("proto/orders.proto")?;
    toni_build::shapes("toni_examples.orders")?;
    Ok(())
}
```

`shapes` takes the same string `tonic::include_proto!` takes, and rewrites the file that macro includes in place: for a service `Orders` it appends an `orders_toni` module of marker types beside the `orders_server` module tonic wrote, one per rpc. `#[grpc_methods]` projects each method's request type through those markers — a macro runs before name resolution and cannot resolve a type it reads off a handler, so this is where the wire shape comes from. Skip the line and the macro expands to a path that does not exist.

Re-running is safe: a second `shapes` call replaces its own section rather than appending another. A file with no service trait in it is an error, not a no-op.

The first step requires `protoc` on the build machine. To vendor it instead (via the `protoc-bin-vendored` build-dependency):

```rust title="build.rs"
fn main() -> Result<(), Box<dyn std::error::Error>> {
    let protoc = protoc_bin_vendored::protoc_bin_path()?;
    // SAFETY: build.rs is single-threaded; setting an env var here is fine.
    unsafe {
        std::env::set_var("PROTOC", protoc);
    }
    tonic_prost_build::compile_protos("proto/orders.proto")?;
    toni_build::shapes("toni_examples.orders")?;
    Ok(())
}
```

For a trait tonic did not write — hand-written, or built through `tonic_build::manual` — use `toni_build::shapes_in_file(path)` and point it at the file that holds the trait.

</Step>

<Step>

### Write the service

`tonic::include_proto!` pulls the generated code into a module. The service is a `#[controller]` struct; its handlers go in an inherent impl marked with the proto trait they serve.

```rust
use std::net::SocketAddr;
use std::sync::Arc;
use std::sync::atomic::{AtomicU64, Ordering};

use toni::extractors::Payload;
use toni::{controller, grpc_methods, injectable, module, new, ToniFactory};

mod orders_pb {
    tonic::include_proto!("toni_examples.orders");
}

// An ordinary provider — nothing gRPC-specific about it.
#[injectable]
pub struct OrdersCounter {
    seq: Arc<AtomicU64>,
}

impl OrdersCounter {
    #[new]
    pub fn new() -> Self {
        Self { seq: Arc::new(AtomicU64::new(1000)) }
    }

    fn next_id(&self) -> u64 {
        self.seq.fetch_add(1, Ordering::SeqCst)
    }
}

// The failure a handler answers with. `kind()` decides the wire code:
// BadRequest is INVALID_ARGUMENT here, 400 on HTTP.
#[derive(Debug, toni::Error)]
enum OrderError {
    #[error_kind(BadRequest)]
    InvalidQty { qty: u32 },
}

impl std::fmt::Display for OrderError {
    fn fmt(&self, f: &mut std::fmt::Formatter<'_>) -> std::fmt::Result {
        match self {
            Self::InvalidQty { qty } => write!(f, "qty must be positive, got {qty}"),
        }
    }
}

impl std::error::Error for OrderError {}

// #[inject] fields resolve from the module's providers.
#[controller]
pub struct OrdersGrpcService {
    #[inject]
    counter: OrdersCounter,
}

// The proto trait is the argument. The macro writes the trait impl around
// these handlers and registers the service with the adapter at bind time.
#[grpc_methods(orders_pb::orders_server::Orders)]
impl OrdersGrpcService {
    #[grpc_method]
    async fn create(
        &self,
        Payload(req): Payload<orders_pb::CreateOrderRequest>,
    ) -> Result<orders_pb::CreateOrderResponse, OrderError> {
        if req.qty == 0 {
            return Err(OrderError::InvalidQty { qty: req.qty });
        }
        Ok(orders_pb::CreateOrderResponse {
            id: self.counter.next_id(),
            status: format!("created:{}", req.item),
        })
    }
}
```

Four rules govern that impl:

- **Each handler is marked.** `#[grpc_method]` for a single reply, `#[grpc_stream]` for a streaming one. Anything unmarked stays exactly as written — the constructor, `#[on_*]` lifecycle hooks, private helpers.
- **Every rpc the proto declares needs a handler.** The generated trait has no default bodies, so a missing one is an unimplemented-trait error at the impl.
- **Every parameter is an extractor**, in any order: `Payload<T>` for the message, `Inbound<T>` for the caller's stream, `Extensions` for the execution's bag, `toni_grpc::GrpcRequest<T>` for the whole tonic request, or any [custom extractor](/docs/extractors/custom) over `GrpcContext`. The one parameter the macro reads by spelling is `&GrpcContext`, which passes through as the context itself rather than being extracted from it. Those first three all take the request, and it is taken once: two of them in one handler is a compile error naming both.
- **The answer is your own type.** The reply message, or `Result<Reply, E>` where `E` implements `toni::Error`. Return `tonic::Response<T>` instead of the bare reply to set reply metadata; drop the `Result` entirely for a handler that cannot fail.

Nothing needs importing from the generated module. The macro names the trait's siblings — the `OrdersServer` wrapper and the `orders_toni` shapes — through the qualified path in the attribute.

`#[controller]` makes the struct a dispatch target: it goes in a module's `controllers` list like an HTTP or RPC controller, and it is not injectable. It is a singleton unless a dependency is request-scoped, in which case it auto-elevates and is built per call. There is no `OrdersServer::new(...)` and no `adapter.add_service(...)` in user code; the `controllers` entry is the entire wiring story.

Two attribute options cover a generated layout that differs from the usual one. `#[grpc_methods(orders_pb::orders_server::Orders, server = path::to::OrdersServer)]` points at a wrapper with a non-standard name or location, and `shapes = path::to::orders_toni` points at a companion module written somewhere other than beside the trait.

</Step>

<Step>

### Wire the module and start

```rust
#[module(controllers: [OrdersGrpcService], providers: [OrdersCounter])]
struct AppModule;

#[tokio::main(flavor = "current_thread")]
async fn main() {
    let local = tokio::task::LocalSet::new();
    local.run_until(async move {
        let addr: SocketAddr = "127.0.0.1:50051".parse().unwrap();
        let mut app = ToniFactory::create(AppModule).await.unwrap();
        app.use_grpc_adapter(toni_grpc::GrpcAdapter::new(addr)).unwrap();
        app.start().await.unwrap();
    }).await;
}
```

### The LocalSet requirement

`ToniFactory` and the application it builds are `!Send` — the DI container is `Rc`-based. Every gRPC example and integration test in the repository runs under `#[tokio::main(flavor = "current_thread")]` with a `tokio::task::LocalSet`, as above. Use this pattern for gRPC `main` functions; the remaining pages in this section assume it and show only the code inside `run_until`.

</Step>

### Smoke-test with grpcurl

```bash
grpcurl -plaintext \
    -d '{"item":"keyboard","qty":3}' \
    -proto proto/orders.proto -import-path proto \
    127.0.0.1:50051 toni_examples.orders.Orders/Create
```

```json
{
  "id": "1000",
  "status": "created:keyboard"
}
```

A complete runnable version — including a guard, an interceptor, and an error handler — lives at `examples/grpc_service.rs` in the repository (`cargo run --example grpc_service`).
