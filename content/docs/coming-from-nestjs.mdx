---
title: Coming from NestJS
description: The decorator-to-macro map, a small NestJS application ported line by line, and the places where Ulo diverges.
---

Ulo takes its architecture from NestJS: modules own controllers and providers, dependencies arrive through a container, and every request passes through guards and interceptors on its way to a handler. If you know that model, you already know how a Ulo application is laid out.

What changes is the language. TypeScript decorators become Rust attribute macros, classes become structs, and a handful of NestJS constructs turn out to be unnecessary once types survive to runtime. This page covers all three: the map, a full port, and the divergences.

## The map

### Declarations

| NestJS | Ulo |
|--------|------|
| `@Module({ ... })` | `#[module(...)]` on a unit struct or an `impl` block |
| `imports` / `controllers` / `providers` / `exports` | same four keys, same meaning |
| `@Global()` | `global: true`, or `.global()` on a `DynamicModule` |
| `@Injectable()` | `#[injectable]` on the struct |
| `@Controller('users')` | `#[controller("/users")]` on the struct; handlers in a `#[routes]` impl |
| `@Get()` `@Post()` `@Put()` `@Delete()` | `#[get]` `#[post]` `#[put]` `#[delete]` |
| `@Patch()` `@Head()` `@Options()` | no verb macro |
| `@Sse()` | `#[sse("/path")]` |
| `@WebSocketGateway()` | `#[websocket_gateway("/path")]`; handlers in a `#[subscriptions]` impl |
| `@SubscribeMessage('event')` | `#[subscribe_message("event")]` |
| `@MessagePattern()` | `#[message_pattern]` in a `#[patterns]` impl on a `#[controller]` struct |
| `@EventPattern()` | `#[event_pattern]` |
| `@GrpcMethod()` | `#[grpc_method]` in a `#[grpc_methods(proto::Trait)]` inherent impl on a `#[controller]` struct |
| `@SetMetadata()` | `#[set_metadata]` |

The verb macros stop at `#[get]`, `#[post]`, `#[put]`, `#[delete]`, and `#[sse]`. Answer a `PATCH`, `HEAD`, or `OPTIONS` request from global middleware instead — it runs before routing and can return a response without reaching a handler.

### The enhancer chain

| NestJS | Ulo |
|--------|------|
| `CanActivate` | `Guard<C>` |
| `NestInterceptor` | `Interceptor<C, R>` |
| `ExceptionFilter` + `@Catch(T)` | `ErrorHandler<C, R>`, usually written as `#[catch(T)]` |
| `NestMiddleware` | `Middleware` |
| `@UseGuards()` `@UseInterceptors()` `@UseFilters()` | `#[use_guards]` `#[use_interceptors]` `#[use_error_handlers]` |
| `useGlobalGuards()` | `use_global_http_guards()`, and one per transport |
| `HttpException` | `HttpError` |
| `RpcException` | `RpcError` |

Ulo auto-detects the role from the trait you implement — there is no marker attribute corresponding to a class implementing `CanActivate`.

### Reading the request

| NestJS | Ulo |
|--------|------|
| `@Param('id')` | a `Path<T>` parameter; the route spells it `{id}` |
| `@Query()` | `Query<T>` |
| `@Body()` | `Json<T>`, or `Body<T>` to accept JSON or form encoding |
| `@Body()` + `ValidationPipe` | `Validated<Json<T>>` |
| `@UploadedFile()` / `@UploadedFiles()` | `Multipart` |
| `@Req()` | `HttpRequest`, or `&HttpContext` as an ordinary parameter |
| `createParamDecorator()` | an `impl FromContext<C> for YourType` |

Extractors are handler parameters, matched by type. There is also a marker form — `#[param]`, `#[query]`, `#[body]` — that reads more like NestJS but carries [its own gotchas](/docs/extractors/markers).

### Custom providers

| NestJS | Ulo |
|--------|------|
| `{ provide: 'TOKEN', useValue: value }` | `provider_value!("TOKEN", value)` |
| `{ provide: 'TOKEN', useFactory: () => fn() }` | `provider_factory!("TOKEN", \|\| fn())` |
| `{ provide: 'TOKEN', useFactory: async (dep) => fn(dep), inject: [Dep] }` | `provider_factory!("TOKEN", async \|dep: Dep\| fn(dep))` |
| `{ provide: 'TOKEN', useExisting: ExistingService }` | `provider_alias!("TOKEN", ExistingService)` |
| `{ provide: TOKEN, useClass: ServiceClass }` | `provider_token!("TOKEN", ServiceClass)` |

The `inject: [...]` array has no counterpart: the factory closure's parameter types are the dependency list.

### Lifecycle hooks

| NestJS interface | Ulo attribute |
|-----------------|----------------|
| `OnModuleInit` | `#[on_module_init]` |
| `OnApplicationBootstrap` | `#[on_application_bootstrap]` |
| `OnModuleDestroy` | `#[on_module_destroy]` |
| `BeforeApplicationShutdown` | `#[before_application_shutdown]` |
| `OnApplicationShutdown` | `#[on_application_shutdown]` |

### Platforms and transports

| NestJS | Ulo |
|--------|------|
| `@nestjs/platform-express`, `-fastify` | `ulo-http-axum`, `ulo-http-actix`, `ulo-http-salvo`, `ulo-http-poem`, `ulo-http-rocket` |
| `Transport.TCP` | `ulo-rpc-tcp` |
| `Transport.NATS` | `ulo-rpc-nats` |
| `Transport.REDIS` | `ulo-rpc-redis` |
| `Transport.RMQ` | `ulo-rpc-rabbitmq` |
| `Transport.MQTT` | `ulo-rpc-mqtt` |
| `Transport.KAFKA` | `ulo-rpc-kafka` |
| `Transport.GRPC` | `ulo-grpc` |

An adapter is registered at runtime and held as a boxed trait object, so application code never names the concrete adapter type — the same property that makes swapping Express for Fastify a one-line change in NestJS.

### Integrations

| NestJS | Ulo |
|--------|------|
| `TypeOrmModule.forRoot()` | `SeaOrmModule::for_root()`, or `SqlxModule::postgres()` for raw SQL |
| `MongooseModule.forRoot()` | `MongoModule::for_root(uri, db)` |
| `PrismaModule` | `PrismaModule::for_root(client)` |
| `ConfigModule.forRoot()` | `ConfigModule::<T>::new()` |
| `@nestjs/terminus` | `ulo-health` |
| `@nestjs/graphql` | `ulo-graphql-async-graphql`, `ulo-graphql-juniper` |
| `@nestjs/testing` | construct the struct directly, or `create_application_context` |

`forRoot()` carries over as `for_root`, and returns a `DynamicModule` you list under `imports:`.

## A NestJS application, ported

The same user resource, written twice. This is the whole of it — service, controller, module, bootstrap.

### The service

```ts
// NestJS
@Injectable()
export class UserService {
  findAll(): User[] { /* ... */ }
  findOne(id: number): User | undefined { /* ... */ }
}
```

```rust
// Ulo
#[injectable]
pub struct UserService;

impl UserService {
    pub fn find_all(&self) -> Vec<User> { /* ... */ }
    pub fn find_one(&self, id: u32) -> Option<User> { /* ... */ }
}
```

`#[injectable]` goes on the struct definition. The `impl` block stays an ordinary Rust `impl` — the framework does not scan it.

### The controller

```ts
// NestJS
@Controller('users')
export class UserController {
  constructor(private readonly service: UserService) {}

  @Get()
  findAll() { return this.service.findAll(); }

  @Get(':id')
  findOne(@Param('id') id: string) { /* ... */ }

  @Post()
  create(@Body() dto: CreateUserDto) { /* ... */ }
}
```

```rust
// Ulo
#[controller("/users")]
pub struct UserController {
    #[inject]
    service: UserService,
}

#[routes]
impl UserController {
    #[get("/")]
    fn find_all(&self) -> Body {
        Body::json(serde_json::json!(self.service.find_all()))
    }

    #[get("/{id}")]
    fn find_one(&self, Path(id): Path<u32>) -> HttpResponse { /* ... */ }

    #[post("/")]
    fn create(&self, Json(dto): Json<CreateUserDto>) -> HttpResponse { /* ... */ }
}
```

Three things move. Constructor injection becomes `#[inject]` fields on the struct. The handlers move out of the type declaration and into a second `impl` block marked `#[routes]` — that block is what gets scanned, and a `#[get]` outside it never registers a route. And the path parameter is `{id}`, not `:id`.

### The module

```ts
// NestJS
@Module({
  controllers: [UserController],
  providers: [UserService],
})
export class AppModule {}
```

```rust
// Ulo
#[module(
  imports: [],
  controllers: [UserController],
  providers: [UserService],
  exports: []
)]
impl AppModule {}
```

A direct mapping. `#[module]` sits on an empty `impl` block, as the CLI generates it, or on a unit struct — `#[module(...)] pub struct AppModule;` is the same thing.

### Bootstrap

```ts
// NestJS
const app = await NestFactory.create(AppModule);
await app.listen(3000);
```

```rust
// Ulo
let mut app = UloFactory::create(AppModule).await.unwrap();
app.use_http_adapter(AxumAdapter::new(), ("127.0.0.1", 3000)).unwrap();
app.start().await.unwrap();
```

`create` takes the root module the way `NestFactory.create` does. There is no `app.listen`: the HTTP server is a separate choice, and `use_http_adapter` is the call that registers every route from the module tree with it.

## Where Ulo diverges

These are the places the map above does not reach — where a NestJS habit produces code that is wrong rather than merely spelled differently.

### There is no `forwardRef`

`forwardRef` defers a class reference that is `undefined` at module-evaluation time. Ulo identifies providers by string token and resolves them at runtime, so a reference is never undefined and there is nothing to defer. A reported cycle is a real construction cycle; break it.

### Guards cannot throw

`can_activate` returns `bool`. There is no `UnauthorizedException` to raise from inside a guard, and `false` produces a 403. To answer with anything else, register a `#[catch(GuardRejection)]` error handler. In exchange, `can_activate` is async — JWT verification and database lookups run inline.

### There is no `ValidationPipe`

NestJS leans on a global `ValidationPipe` because TypeScript types are erased at runtime. In Ulo, `Path<i32>` parses and `Validated<Json<T>>` validates, both declared in the handler signature and enforced by the compiler. `Validated<E>` validates whatever extractor `E` wraps, on any transport — `Validated<Payload<T>>` checks an RPC message or a WebSocket frame the same way. A check that needs a dependency, or one spanning several extracted values, belongs in a guard or in a custom `FromContext` extractor.

### Error handlers are the override, not the default

A `#[derive(ulo::Error)]` type carries an `ErrorKind` and renders itself — return it with `?` and the response is already correct. `#[catch(T)]` is how you override that rendering for one type, not how errors normally become responses.

### Globals are registered per transport

`useGlobalGuards` has no single counterpart. Each transport registers its own: `use_global_http_guards`, `use_global_ws_guards`, `use_global_rpc_guards`, `use_global_grpc_guards` — and the same four-way split for interceptors and error handlers. `use_global_middleware` is the one call without a transport in its name, and it applies to HTTP only.

### The global middleware chain runs before routing

Middleware registered on the factory runs before route resolution on all five HTTP adapters, so it observes 404s, 405s, and same-port WebSocket upgrades, and a URI rewrite inside it changes which route matches. Module-scoped middleware — the `configure_middleware` form that mirrors `NestModule.configure` — stays post-routing, on the matched route only.

### Request scope means one execution, not one HTTP request

A request-scoped provider is built once per *execution*: one HTTP request, one WebSocket message, one RPC or gRPC call, or one standalone execution opened with `ProviderContext::standalone()`. For a WebSocket gateway that means per message, not per connection — per-connection state belongs in the [session](/docs/websocket/gateways).

### Nothing handles signals for you

NestJS starts running shutdown hooks on SIGTERM once `enableShutdownHooks()` is called. Ulo installs no signal handlers. Wire SIGTERM and SIGINT to a `ShutdownHandle` yourself, or the hooks never run — see [Graceful Shutdown](/docs/techniques/graceful-shutdown).

### Startup has three phases, and each can fail

`create` resolves the dependency graph and runs init hooks. `bind` acquires sockets. `run` serves. All four constructors return `Result`, and `bind` is refuse-or-none: a transport that fails takes the whole application down and closes whatever was already acquired. Registration precedes acquisition for HTTP, WebSocket, and gRPC, so a misconfiguration on those reports before a port conflict does; `ulo-rpc-tcp` and `ulo-rpc-udp` take their socket while registering, and can report a conflict first. Nothing calls `process::exit`.

### The application is `!Send`

The container is `Rc<RefCell<_>>`, so the app cannot cross threads. `main` can still `await` it on any runtime — that is what the quick start does, and `block_on` accepts a `!Send` future. A `tokio::task::LocalSet` and `spawn_local` are needed only when the application is *spawned* rather than awaited: a gRPC server, or several applications sharing one thread. Handlers and providers are unaffected; this constrains only how you start the process.
