RPC controllers are the microservice equivalent of HTTP controllers. They group pattern-matched message handlers. Like HTTP controllers, they are dispatch targets, not providers — the framework builds them to route messages, and nothing injects one.

## Defining a controller

`#[controller]` goes on the struct — dependencies are `#[inject]` fields, exactly as with `#[injectable]`. A `#[patterns]` attribute on the impl block scans the handlers and names RPC as the transport. The DI constructor is marked `#[new]`:

```rust
use ulo::{controller, module, new, patterns};

#[controller]
pub struct OrdersController {
    #[inject]
    service: OrdersService,
}

#[patterns]
impl OrdersController {
    #[new]
    pub fn new(service: OrdersService) -> Self {
        Self { service }
    }

    // handlers go here
}
```

Register it in a module's `controllers` list — its dependencies stay in `providers`:

```rust
#[module(controllers: [OrdersController], providers: [OrdersService])]
pub struct OrdersModule;
```

<Callout type="warn">
Listing an RPC controller under `providers` is a compile error — no provider factory exists for it. When a dependency is request-scoped, the controller auto-elevates and is built per call, exactly as HTTP controllers do.
</Callout>

The handler impl is what makes a controller an RPC controller: a `#[controller]` struct with no `#[patterns]` impl dispatches nothing on any transport. An **empty** `#[patterns]` impl is the RPC controller that routes nothing — it registers as a dispatch target with no patterns.

## Handler parameters

Every handler parameter is an extractor — a type implementing `FromContext<RpcContext>` — and a handler takes them in any order, or takes none. `&RpcContext` is the exception: it is the context itself, passed through wherever it sits in the signature.

| Parameter | What it carries |
|---|---|
| `Payload<T>` | the call's data, deserialized into `T` |
| `RpcData` | the call's data, untouched |
| `Validated<Payload<T>>` | the same deserialization, then the `validator` rules `T` declares |
| `Extensions` | the per-call typed bag an enhancer filled |
| `&RpcContext` | the context |

A parameter of a type that is not a `FromContext<RpcContext>` fails to compile at that parameter, naming the type and the context it cannot be read from. Your own extractors work here as they do on HTTP — see [Custom extractors](/docs/extractors/custom).

The `Ok` side of the return can be `RpcData` (forwarded as-is) or any `Serialize` type (serialized into the reply):

```rust
use ulo::extractors::Payload;

#[derive(serde::Deserialize)]
struct CreateOrderDto {
    item: String,
    qty: u32,
}

#[derive(serde::Serialize)]
struct OrderDto {
    id: u64,
    item: String,
    qty: u32,
    status: &'static str,
}

#[patterns]
impl OrdersController {
    #[new]
    pub fn new(service: OrdersService) -> Self {
        Self { service }
    }

    #[message_pattern("order.create")]
    async fn create_order(
        &self,
        Payload(payload): Payload<CreateOrderDto>,
    ) -> Result<OrderDto, ulo::RpcError> {
        if payload.qty == 0 {
            return Err(ulo::RpcError::Internal("qty must be positive".into()));
        }
        Ok(self.service.create_order(&payload.item, payload.qty))
    }
}
```

An extraction that fails never reaches the handler: the failure becomes an `RpcError::Internal` carrying the extractor's own message, is offered to the error chain, and unclaimed renders as an error envelope with kind `Internal` (see [Errors on the wire](#errors-on-the-wire)).

`Validated<Payload<T>>` runs `T`'s `#[validate]` rules after deserializing, so a handler that would otherwise open with a manual check takes the validated value directly:

```rust
use ulo::extractors::{Payload, Validated};

#[derive(serde::Deserialize, validator::Validate)]
struct CreateOrderDto {
    #[validate(length(min = 1))]
    item: String,
    #[validate(range(min = 1))]
    qty: u32,
}

#[message_pattern("order.create")]
async fn create_order(
    &self,
    Validated(Payload(payload)): Validated<Payload<CreateOrderDto>>,
) -> Result<OrderDto, ulo::RpcError> {
    Ok(self.service.create_order(&payload.item, payload.qty))
}
```

Taking `RpcData` instead hands the handler the raw payload, and returning `RpcData` sends it back untouched:

```rust
#[message_pattern("order.create")]
async fn create_order(
    &self,
    data: ulo::RpcData,
    _ctx: &ulo::RpcContext,
) -> Result<ulo::RpcData, ulo::RpcError> {
    let payload = data
        .as_json()
        .ok_or_else(|| ulo::RpcError::Internal("expected JSON payload".into()))?;

    let item = payload["item"].as_str().unwrap_or("unknown");
    let qty = payload["qty"].as_u64().unwrap_or(1) as u32;

    Ok(ulo::RpcData::json(self.service.create_order(item, qty)))
}
```

`Extensions` reads what an earlier stage attached — a guard's authenticated caller, an interceptor's tenant:

```rust
use ulo::context::Extensions;
use ulo::extractors::Payload;

#[message_pattern("order.create")]
async fn create_order(
    &self,
    Payload(payload): Payload<CreateOrderDto>,
    ext: Extensions,
) -> Result<OrderDto, ulo::RpcError> {
    let caller = ext.get::<AuthenticatedUser>(); // attached by a guard
    Ok(self.service.create_order(&payload.item, payload.qty))
}
```

## Request-response vs fire-and-forget

`#[message_pattern]` marks a handler whose result is sent back to the caller.

`#[event_pattern]` marks a handler for events with no reply. It must return `Result<(), RpcError>` — any other return type is a compile error:

```rust
use ulo::extractors::Payload;

#[event_pattern("order.shipped")]
async fn on_order_shipped(
    &self,
    Payload(payload): Payload<ShipOrderDto>,
) -> Result<(), ulo::RpcError> {
    self.service.handle_shipment(payload.order_id);
    Ok(())
}
```

When a caller addresses an `#[event_pattern]` handler but requests a reply anyway (sends a correlation id / reply-to), the adapter sends a `null` ack so the caller's pending request closes instead of timing out.

## Streaming replies

A `#[message_pattern]` handler can answer with a sequence of frames instead of one. Declare `-> RpcHandlerResult` and return the `Stream` variant:

```rust
use futures::StreamExt;
use ulo::rpc::{RpcHandlerOutput, RpcHandlerResult};

#[message_pattern("feed.count")]
async fn count(&self, _d: ulo::RpcData) -> RpcHandlerResult {
    Ok(RpcHandlerOutput::Stream(
        futures::stream::iter(
            (1..=3).map(|n| Ok(ulo::RpcData::json(serde_json::json!(n)))),
        )
        .boxed(),
    ))
}
```

`RpcHandlerResult` is `Result<RpcHandlerOutput, RpcError>`, and `RpcHandlerOutput` has three shapes:

```rust
RpcHandlerOutput::Empty                 // no reply — what an #[event_pattern] handler answers
RpcHandlerOutput::Single(RpcData)       // one reply
RpcHandlerOutput::Stream(BoxStream<'static, Result<RpcData, RpcError>>)
```

Declaring the alias as the return type is the entire opt-in: the pattern attribute is the same one, and a handler returning `Result<T, RpcError>` keeps its serialize-the-reply behavior.

The adapter drains the stream to the caller frame by frame and closes it with an end marker. Every transport speaks the same grammar:

| Frame | Body |
|---|---|
| item (`Json` / `Text`) | `{"stream": <value>}` |
| item (`Binary`) | `{"stream_b64": "<base64>"}` |
| clean end | `{"end": true}` |
| error end | `{"end": true, "err": {"message": ..., "status": ...}}` |

An item frame is always JSON so the end marker stays distinguishable from it, which is why binary items travel base64 under a key of their own. TCP and UDP splice the call's `id` into every frame; the brokers correlate the way they correlate a single reply. Each transport page states its carrier.

### Fallible items

An item is a `Result`, and an `Err` item ends the stream. Which closing frames it produces follows the same two lanes a single reply takes: a domain error (`AppError`) becomes a final data frame carrying the canonical error envelope followed by a clean end, so the caller reads it as data; `PatternNotFound` / `Forbidden` / `Internal` become an error end, which the caller's stream yields as its failure.

A mid-stream `Err` reaches no error handler. The pipeline returned when the handler produced the stream — before any item existed — so there is no seam left to claim it.

### Consuming a stream

`RpcClient::stream` returns an `RpcReplyStream`, which yields `Result<RpcData, RpcClientError>` until the server's end marker:

```rust
use futures::StreamExt;

let mut items = self.feed
    .stream("feed.count", RpcData::json(serde_json::json!(null)))
    .await?;

while let Some(item) = items.next().await {
    let data = item?;
    println!("{data:?}");
}
```

`stream_json` serializes the request and parses each item into a type, mirroring `send_json`. On a transport with no streaming support the call fails with `RpcClientError::StreamingUnsupported`.

The transport's `with_timeout` means something different for a streaming call: it bounds the gap to the *next* frame, the first frame included, and expiry arrives as an `Err(RpcClientError::Timeout)` item rather than an error from the call that opened the stream.

### Cancellation

The execution rides the stream — the context, its cache and its cancellation token stay alive as long as frames are still owed. Dropping the reply stream before its end fires the token, and so does a dropped connection, a shutdown, or the caller's cancel notice.

A producer that outlives the handler body — a spawned task feeding a channel — is the case that needs the token, because nothing else tells it the caller left:

```rust
use std::time::Duration;

use futures::StreamExt;
use ulo::context::HandlerContext;
use ulo::rpc::{RpcHandlerOutput, RpcHandlerResult};
use ulo::{RpcContext, RpcData, RpcError};

#[message_pattern("feed.ticks")]
async fn ticks(&self, ctx: &RpcContext) -> RpcHandlerResult {
    let (tx, rx) = tokio::sync::mpsc::channel::<Result<RpcData, RpcError>>(1);
    let token = ctx.cancellation().clone();

    tokio::spawn(async move {
        let mut n = 0u64;
        loop {
            tokio::select! {
                _ = token.cancelled() => break,
                _ = tokio::time::sleep(Duration::from_millis(200)) => {
                    n += 1;
                    let tick = RpcData::json(serde_json::json!({ "tick": n }));
                    if tx.send(Ok(tick)).await.is_err() {
                        break;
                    }
                }
            }
        }
    });

    Ok(RpcHandlerOutput::Stream(
        tokio_stream::wrappers::ReceiverStream::new(rx).boxed(),
    ))
}
```

`cancellation()` comes from the `HandlerContext` trait, so the import is needed even though the method is called on `RpcContext`. Wrapping a receiver as a stream needs `tokio-stream`. `examples/rpc_streaming.rs` in the repository runs both halves of this against the TCP transport.

## RpcData

`RpcData` is the payload carrier with three variants:

```rust
RpcData::Json(serde_json::Value)
RpcData::Text(String)
RpcData::Binary(Vec<u8>)
```

Constructors and accessors:

```rust
RpcData::json(serde_json::json!({ "key": "value" }))
RpcData::text("hello")
RpcData::binary(vec![0u8, 1, 2])

data.as_json()    // Option<&serde_json::Value>
data.as_text()    // Option<&str>
data.as_binary()  // Option<&[u8]>
```

`parse` deserializes any variant as JSON (`Json` via `from_value`, `Text` via `from_str`, `Binary` via `from_slice`); `from_serialize` builds an `RpcData::Json` from any `Serialize` type:

```rust
let dto: CreateOrderDto = data.parse()?;
let reply = RpcData::from_serialize(&order)?;
```

## RpcContext

Handlers can take `&RpcContext` in any position. Its fields are private — read through methods:

```rust
ctx.pattern()        // &str — the matched pattern
ctx.headers()        // &HashMap<String, String> — the wire fields the call arrived with
ctx.header("key")    // Option<&str>
ctx.data()           // &RpcData — the raw inbound payload
ctx.metadata()       // Option<&Metadata> — what #[set_metadata] declared on the handler
```

Headers and metadata are distinct: `headers()` is what the caller sent with this call; `metadata()` is what the handler declared about itself. `#[set_metadata]` goes on the `#[patterns]` impl (every handler) or on an individual handler, and reads back through `ctx.metadata()` — typically from a guard.

Enhancers share the same `&RpcContext`. `RpcContext` implements `HandlerContext`, and `extensions()`, `cache()`, `cancellation()` and `metadata()` work as on every context type — all four come from that trait, so reading them needs `use ulo::context::HandlerContext;` in scope. `extensions()` is the per-call typed bag; it mutates through `&self`, so a guard can `ctx.extensions().insert(v)` for a later stage to read. An adapter that puts a value on the inbound call seeds the same bag, so what a transport attaches is readable from a guard, an interceptor and the handler alike.

Where headers travel on the wire is transport-specific: NATS headers, AMQP headers, MQTT v5 user properties, Kafka headers, a `metadata` field in the TCP/UDP frame, or the Redis request envelope. Each transport page states its mapping.

## RpcError

```rust
RpcError::PatternNotFound(String)   // no handler matched the pattern
RpcError::Forbidden(String)         // a guard rejected the message
RpcError::Internal(String)          // generic server-side failure
RpcError::AppError(Arc<dyn Error>)  // a domain error implementing ulo::Error
```

`AppError` is not built by hand. Any type implementing `ulo::Error` converts into `RpcError` via a blanket `From`, so domain errors lift with `?`. `#[derive(ulo::Error)]` supplies the trait impl, with `#[error_kind(...)]` picking the `ErrorKind`; `Display` and `std::error::Error` impls are still required (a `thiserror` derive fits):

```rust
use ulo::extractors::Payload;

#[derive(Debug, ulo::Error)]
enum OrderError {
    #[error_kind(NotFound)]
    Missing(u64),
}

impl std::fmt::Display for OrderError {
    fn fmt(&self, f: &mut std::fmt::Formatter<'_>) -> std::fmt::Result {
        match self {
            Self::Missing(id) => write!(f, "order {id} not found"),
        }
    }
}

impl std::error::Error for OrderError {}

#[message_pattern("order.get")]
async fn get_order(
    &self,
    Payload(id): Payload<u64>,
) -> Result<OrderDto, ulo::RpcError> {
    let order = self.service.find(id).ok_or(OrderError::Missing(id))?;
    Ok(order)
}
```

The handler's declared error type can also be the domain error itself — `Result<OrderDto, OrderError>` — and the macro converts it to `RpcError` at the dispatch boundary.

## Errors on the wire

Two lanes carry a failure back, and which one a caller sees says where the failure happened.

An error **the pipeline answered with** — any `RpcError` a handler returned, a lifted domain error, a failed extraction, or a recovered panic — is rendered as the canonical error envelope and delivered as a normal reply:

```json
{"response": {"status": "error", "kind": "Internal", "message": "qty must be positive"}}
```

`kind` is `Internal` / `NotFound` / `Forbidden` for the framework variants, or the domain error's `kind()` name for `AppError`; a domain error's `details()` merge in as a `details` field.

A panic in anything a user wrote — a guard, an interceptor, the handler body, a `#[new]` constructor — is caught and delivered to the error-handler chain as `PanicRecovered`, narrated at `debug`. Unclaimed, it renders through the same envelope with kind `Internal` and a message naming the segment it came from: `panic recovered in handler: <panic text>`. The connection stays usable either way.

A wire-level **error frame** is what the framework writes when dispatch itself failed and there is no handler answer to render:

```json
{"err": {"message": "Pattern not found: does.not.exist", "status": "not_found"}}
```

| `status` | Cause |
|---|---|
| `not_found` | no handler registered for the pattern |
| `forbidden` | a guard rejected the message and no error handler claimed the rejection |
| `error` | an interceptor returned an `Err` of its own |
| `overloaded` | TCP/UDP only — `with_max_inflight` cap reached |

A handler's own `RpcError::Internal` is not on this lane — like every other answered error it rides inside `response`.

On the client, error frames surface as `RpcClientError::Remote { message, status }`. Envelope errors arrive as ordinary reply data — a raw `send` returns them as `RpcData`, and a typed `send_json::<_, R>` fails to decode into `R` unless `R` accommodates the envelope shape.

## Guards, interceptors, error handlers

Enhancers are plain `#[injectable]` providers implementing the typed traits — `Guard<RpcContext>`, `Interceptor<RpcContext, RpcHandlerResult>`, `ErrorHandler<RpcContext, RpcData>` — where `RpcHandlerResult = Result<RpcHandlerOutput, RpcError>` is what the transport answers with:

```rust
use ulo::traits_helpers::Guard;
use ulo::{async_trait, injectable, RpcContext};

#[injectable]
pub struct ApiKeyGuard {}
impl ApiKeyGuard {}

#[async_trait]
impl Guard<RpcContext> for ApiKeyGuard {
    async fn can_activate(&self, ctx: &RpcContext) -> bool {
        ctx.header("api-key") == Some("secret")
    }
}
```

An interceptor sees `RpcHandlerOutput::Stream` as an opaque variant. The execution is attached to whatever stream the chain returns, so an interceptor that substitutes its own drops the handler's before it was ever attached — that discarded stream fires no cancellation token.

Apply with `#[use_guards]` / `#[use_interceptors]` / `#[use_error_handlers]` — on the `#[patterns]` impl for every handler in the controller, or on an individual handler:

```rust
use ulo::extractors::Payload;

#[patterns]
#[use_interceptors(RpcLoggingInterceptor)]   // controller-level
impl OrdersController {
    #[new]
    pub fn new(service: OrdersService) -> Self {
        Self { service }
    }

    #[message_pattern("order.create")]
    #[use_guards(ApiKeyGuard)]               // handler-level
    async fn create_order(
        &self,
        Payload(payload): Payload<CreateOrderDto>,
    ) -> Result<OrderDto, ulo::RpcError> {
        // ...
    }
}
```

Enhancers are ordinary providers, so they go in the module's `providers` list — the controller they attach to stays in `controllers`. Guards return `bool` and cannot attach an error of their own, but a rejection is offered to the error chain first: a `#[catch(GuardRejection)]` handler reshapes the refusal into whatever the caller should see, and only an unclaimed rejection becomes the `forbidden` error frame.

Global RPC enhancers register on the factory before the app is created:

```rust
let mut factory = UloFactory::new();
factory.use_global_rpc_guards(Arc::new(ApiKeyGuard {}));
let mut app = factory.create_with(AppModule).await?;
```

`use_global_rpc_interceptors` and `use_global_rpc_error_handler` follow the same shape, taking `Arc<dyn Interceptor<RpcContext, RpcHandlerResult>>` and `Arc<dyn ErrorHandler<RpcContext, RpcData>>`.

## RpcClient

To send messages from one service to another, inject an `RpcClient`. Construct it with any client transport and register it under a token:

```rust
use ulo::{provider_value, RpcClient};
use ulo_rpc_nats::NatsClientTransport;

#[module(
    providers: [
        OrdersService,
        provider_value!(
            "INVENTORY_CLIENT",
            RpcClient::new(NatsClientTransport::new("nats://127.0.0.1:4222"))
        ),
    ],
)]
pub struct OrdersModule;
```

```rust
#[injectable]
pub struct OrdersService {
    #[inject("INVENTORY_CLIENT")]
    inventory: RpcClient,
}

impl OrdersService {
    pub async fn check_stock(&self, item_id: u64) -> Result<bool, RpcClientError> {
        let reply = self.inventory
            .send("inventory.check", RpcData::json(serde_json::json!({ "id": item_id })))
            .await?;
        reply.parse().map_err(|e| RpcClientError::Transport(e.to_string()))
    }

    pub async fn notify_restock(&self, item_id: u64) -> Result<(), RpcClientError> {
        self.inventory
            .emit("inventory.restock", RpcData::json(serde_json::json!({ "id": item_id })))
            .await
    }
}
```

`send` is request-response; `emit` is fire-and-forget; `stream` opens a [streaming call](#streaming-replies).

### Typed helpers

`send_json` and `emit_json` serialize the input and (for `send_json`) deserialize the reply; `stream_json` does the same per item:

```rust
let status: StockStatus = self.inventory
    .send_json("inventory.status", &CheckRequest { item_id })
    .await?;

self.inventory
    .emit_json("inventory.restock", &RestockRequest { item_id, qty: 100 })
    .await?;

let mut levels = self.inventory
    .stream_json::<_, StockLevel>("inventory.watch", &WatchRequest { item_id })
    .await?;
```

### Per-call headers

`request(pattern)` opens a builder that attaches header entries (auth tokens, trace ids, tenant) before dispatch. Finish with `send` / `emit` / `stream` or their `_json` variants:

```rust
self.inventory
    .request("inventory.restock")
    .header("trace-id", trace_id)
    .header("tenant", tenant)
    .send(RpcData::json(payload))
    .await?;
```

The server reads these through `ctx.headers()` / `ctx.header(key)`. Only the builder carries headers — the plain `send` / `emit` / `stream` shorthands send none. On the JSON-envelope transports (TCP, UDP, Redis) the wire key for these entries remains `metadata`.

### Connection lifecycle

Transports connect lazily on the first `send`, `emit` or `stream`. `connect()` establishes the connection eagerly — call it in an `#[on_application_bootstrap]` hook to surface connection failures at startup. `close()` flushes pending messages and closes; call it in an `#[on_application_shutdown]` hook.

### RpcClientError

```rust
RpcClientError::Transport(String)              // connection or I/O error
RpcClientError::Timeout                        // no reply within the timeout (default 5 s)
RpcClientError::Remote { message, status }     // the remote returned an error frame
RpcClientError::StreamingUnsupported           // the transport cannot open a streaming call
```
