---
title: TCP Adapter
description: Newline-delimited JSON over raw TCP connections — server and client transport setup.

The TCP adapter runs a raw TCP server that speaks a newline-delimited JSON protocol. It requires no message broker and has no external dependencies beyond Tokio.

## Server setup

Add the dependencies:

```toml title="Cargo.toml"
[dependencies]
toni = "0.2"
toni-tcp = "0.1"
```

Register the adapter after creating the application:

```rust
use toni::ToniFactory;
use toni_tcp::TcpAdapter;

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let mut app = ToniFactory::create(AppModule).await?;
    app.use_rpc_adapter(TcpAdapter::new("0.0.0.0", 4000))?;
    app.start().await?;
    Ok(())
}
```

<Callout type="info">
The socket is bound synchronously during startup, so a port conflict surfaces as an `Err` from `app.start()` (or `app.bind()`) rather than a panic in a background task. Binding port `0` picks a free port; the bound address is available from `app.bind()`'s `BoundAdapters`.
</Callout>

`TcpAdapter::from_listener(std::net::TcpListener)` serves on a socket the caller already bound and put into listening state instead of binding one — the route to systemd socket activation and zero-downtime restarts; see [Bind targets](/docs/techniques/bind-targets).

### Adapter options

```rust
use std::time::Duration;

TcpAdapter::new("0.0.0.0", 4000)
    .with_drain_timeout(Duration::from_secs(30))  // default 10 s; None = wait without bound
    .with_max_inflight(512)                       // default unbounded
```

- `with_drain_timeout` — how long `close()` waits for in-flight requests before aborting them. On shutdown the accept loop stops, connections stop reading new lines, and in-flight handler tasks are drained up to this timeout.
- `with_max_inflight` — caps concurrently running handler tasks across all connections. A request over the cap is rejected immediately with an `overloaded` error frame; a fire-and-forget message over the cap is dropped with a log line.

## Wire protocol

All frames are newline-terminated JSON objects (`\n` delimiter). Inbound:

```json
{"pattern": "order.create", "data": {"item": "book", "qty": 2}, "id": "42", "metadata": {"trace-id": "abc"}}
```

- `id` — optional correlation id. Present means the caller expects a reply; absent means fire-and-forget.
- `metadata` — optional object of string values, surfaced as `ctx.headers()`. Non-string values are skipped.

One response frame per request:

```json
{"id": "42", "response": {"orderId": 1001}}
```

A handler error arrives as a reply carrying the canonical error envelope:

```json
{"id": "42", "response": {"status": "error", "kind": "Internal", "message": "out of stock"}}
```

A dispatch failure arrives as an error frame:

```json
{"id": "42", "err": {"message": "Pattern not found: does.not.exist", "status": "not_found"}}
```

Statuses: `not_found`, `forbidden`, `error`, `overloaded` — see [Errors on the wire](/docs/microservices/rpc-controllers#errors-on-the-wire).

Two edge cases:

- A frame with an `id` that lands on an `#[event_pattern]` handler gets an explicit ack, `{"id": "42", "response": null}`, so the caller does not time out.
- A handler panic is caught and answered as a reply carrying the `Internal` envelope, `{"id": "42", "response": {"status": "error", "kind": "Internal", "message": "panic recovered in handler: ..."}}`; the connection stays open. A panic escaping the dispatcher itself is the last-resort case and yields `{"id": "42", "err": {"message": "internal server error", "status": "error"}}`.

### Streaming replies

A [streaming reply](/docs/microservices/rpc-controllers#streaming-replies) is item frames closed by an end marker, every frame carrying the call's `id`:

```json
{"id": "42", "stream": {"tick": 1}}
{"id": "42", "stream_b64": "AAEC"}
{"id": "42", "end": true}
```

`stream_b64` carries an `RpcData::Binary` item base64-encoded. An abnormal end is `{"id": "42", "end": true, "err": {"message": "...", "status": "error"}}`.

The caller abandons an in-flight call — mid-handler or mid-stream — by sending `{"id": "42", "cancel": true}` on the same connection: the driving task is aborted and the handler's execution hears its cancellation token. A dropped connection cancels everything that connection still had in flight.

Test with netcat:

```bash
echo '{"pattern":"order.create","data":{"item":"keyboard","qty":3},"id":"req-1"}' | nc 127.0.0.1 4000
```

## Client transport

`TcpClientTransport` maintains one persistent connection to the remote server. Request-response multiplexes over it via correlation ids; a background reader routes each reply to the waiting caller:

```rust
use toni::{provider_value, RpcClient};
use toni_tcp::TcpClientTransport;

provider_value!(
    "ORDERS_CLIENT",
    RpcClient::new(TcpClientTransport::new("127.0.0.1", 4000))
)
```

The connection is established lazily on the first `send` or `emit`. After a fatal error (connection closed, write failure) the cached connection is dropped and the next call reconnects; requests pending at the moment of failure fail with `RpcClientError::Transport("connection closed")`.

### Custom timeout

The default request-response timeout is 5 seconds:

```rust
use std::time::Duration;

RpcClient::new(
    TcpClientTransport::new("127.0.0.1", 4000)
        .with_timeout(Duration::from_secs(10))
)
```

For a streaming call the same setting bounds the gap to the next frame, the first frame included. Expiry arrives as an `Err(RpcClientError::Timeout)` item and sends the cancel frame, so the server stops producing.

A `send()` that receives a stream frame fails with `RpcClientError::Transport("streaming reply to a single-reply call — use stream()")` — a single-reply call has nowhere to put the frames that follow.

## Payload limitations

The wire format is JSON, so a request payload and a single reply cannot carry `RpcData::Binary` — on the wire it becomes `null`. Encode binary data (e.g. base64) into `RpcData::Json` or `RpcData::Text` instead. A binary *stream item* is the exception: it travels base64-encoded under the `stream_b64` key.

## Tracing

Every inbound message runs inside an `rpc.request` span with `transport="tcp"`, `pattern`, `id`, and `peer` fields. Events emitted from handlers inherit them, so log lines correlate back to the originating message without any handler-side plumbing.

## Example

```rust
use toni::{controller, injectable, module, new, patterns, serde_json, ToniFactory};

#[injectable]
pub struct OrdersService {}
impl OrdersService {
    pub fn create_order(&self, item: &str, qty: u32) -> serde_json::Value {
        serde_json::json!({ "id": 1001, "item": item, "qty": qty, "status": "created" })
    }
}

#[controller]
pub struct OrdersController {
    #[inject]
    service: OrdersService,
}

#[patterns]
impl OrdersController {
    #[new]
    pub fn new(service: OrdersService) -> Self {
        Self { service }
    }

    #[message_pattern("order.create")]
    async fn create(
        &self,
        data: toni::RpcData,
        _ctx: &toni::RpcContext,
    ) -> Result<toni::RpcData, toni::RpcError> {
        let payload = data
            .as_json()
            .ok_or_else(|| toni::RpcError::Internal("expected JSON payload".into()))?;
        let item = payload["item"].as_str().unwrap_or("unknown");
        let qty = payload["qty"].as_u64().unwrap_or(1) as u32;
        Ok(toni::RpcData::json(self.service.create_order(item, qty)))
    }

    #[event_pattern("order.shipped")]
    async fn shipped(
        &self,
        data: toni::RpcData,
        _ctx: &toni::RpcContext,
    ) -> Result<(), toni::RpcError> {
        let order_id = data.as_json().and_then(|v| v["order_id"].as_u64()).unwrap_or(0);
        println!("order {order_id} shipped");
        Ok(())
    }
}

#[module(controllers: [OrdersController], providers: [OrdersService])]
struct AppModule;

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let mut app = ToniFactory::create(AppModule).await?;
    app.use_rpc_adapter(toni_tcp::TcpAdapter::new("0.0.0.0", 4000))?;
    app.start().await?;
    Ok(())
}
```
