Toni supports microservice communication through an **RPC transport layer** that is completely decoupled from HTTP. The same module and DI system used for HTTP controllers applies to RPC — services share one container, controllers get injected dependencies, lifecycle hooks run the same way.

## How it works

An RPC application runs alongside (or instead of) an HTTP server. After creating the application, register a transport adapter and start:

```rust
use toni::ToniFactory;
use toni_tcp::TcpAdapter;

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let mut app = ToniFactory::create(AppModule).await?;
    app.use_rpc_adapter(TcpAdapter::new("0.0.0.0", 4000))?;
    app.start().await?;
    Ok(())
}
```

HTTP and RPC can run on the same application instance:

```rust
let mut app = ToniFactory::create(AppModule).await?;
app.use_http_adapter(AxumAdapter::new(), ("0.0.0.0", 3000))?;
app.use_rpc_adapter(TcpAdapter::new("0.0.0.0", 4000))?;
app.start().await?;
```

An application holds one RPC adapter — a second `use_rpc_adapter` call replaces the first. To serve the same controllers over two transports, create two application instances from the same module.

gRPC is not part of this layer: it is contract-first — services and messages are declared in `.proto` files and known at compile time — which does not fit the pattern-string + payload model. It registers separately via `use_grpc_adapter` with the `toni-grpc` crate.

## Message routing

Each RPC controller method is bound to a **pattern** — a string that identifies the operation. Inbound messages are dispatched to the handler whose pattern matches the message's pattern exactly. What the pattern maps to on the wire (TCP frame field, NATS subject, Redis channel, queue, topic) is the transport's choice.

Two handler kinds exist:

| Annotation | Direction | Handler return |
|---|---|---|
| `#[message_pattern("op")]` | Request-response — a reply is sent back | `Result<T, RpcError>` where `T` is `RpcData` or any `Serialize` type |
| `#[message_pattern("op")]` | Request-response, many replies | `RpcHandlerResult` — the output passes through untouched, which is how a handler [streams](/docs/microservices/rpc-controllers#streaming-replies) |
| `#[event_pattern("op")]` | Fire-and-forget — no reply | `Result<(), RpcError>` |

Handlers, payload typing, errors, and enhancers are covered in [RPC Controllers](/docs/microservices/rpc-controllers).

## Calling another service

There is no client module to import. A client is one expression — a transport wrapped in an `RpcClient` — registered as an ordinary provider under a string token:

```rust
use toni::{provider_value, RpcClient};
use toni_tcp::TcpClientTransport;

#[module(
    providers: [
        InventoryService,
        provider_value!(
            "ORDERS_CLIENT",
            RpcClient::new(TcpClientTransport::new("127.0.0.1", 4000))
        ),
    ],
)]
struct AppModule;
```

Inject it by that token wherever a service makes the call:

```rust
#[injectable]
pub struct InventoryService {
    #[inject("ORDERS_CLIENT")]
    orders: RpcClient,
}

impl InventoryService {
    pub async fn get_order(&self, id: u64) -> Result<serde_json::Value, RpcClientError> {
        self.orders
            .send_json("order.get", &serde_json::json!({ "id": id }))
            .await
    }
}
```

The token is what makes room for more than one: two clients of the same transport, or one transport pointed at two peers, differ only in the string they register under. When the address comes from configuration rather than a literal, register through a factory that takes the dependency it needs:

```rust
use toni::{provider_factory, RpcClient};
use toni_nats::NatsClientTransport;

provider_factory!("ORDERS_CLIENT", |config: ConfigService<AppConfig>| {
    RpcClient::new(NatsClientTransport::new(config.get_ref().nats_url.clone()))
})
```

`send` is request-response, `emit` is fire-and-forget, and `stream` opens a call whose reply is a sequence of frames. Every client transport connects lazily on the first call and defaults to a 5-second request-response timeout, overridable with `with_timeout`. A peer that is down cannot fail your boot; reaching a dead peer is an ordinary error at the call site. Call `connect()` in an `#[on_application_bootstrap]` hook when you would rather learn at startup.

Forwarding an inbound call's headers to an outbound one is a per-call decision: the handler holds the context, reads `ctx.headers()`, and attaches what it wants through `request(pattern).header(...)`. Nothing propagates on its own.

The full client API — typed helpers, per-call headers, streaming, `connect`/`close` — is documented in [RPC Controllers](/docs/microservices/rpc-controllers#rpcclient).

## Available transports

Each transport ships as its own crate with a server adapter and a client transport:

| Transport | Crate | Pattern maps to | Request-response via |
|---|---|---|---|
| [TCP](/docs/microservices/tcp-adapter) | `toni-tcp` | frame `pattern` field | correlation `id` on a persistent connection |
| [UDP](/docs/microservices/udp-adapter) | `toni-udp` | datagram `pattern` field | correlation `id`, one datagram per message |
| [NATS](/docs/microservices/nats-adapter) | `toni-nats` | subject | built-in reply-to inbox |
| [Redis](/docs/microservices/redis-adapter) | `toni-redis-rpc` | Pub/Sub channel | reply channel carried in a request envelope |
| [RabbitMQ](/docs/microservices/rabbitmq-adapter) | `toni-rabbitmq` | queue | AMQP `reply_to` + `correlation_id` |
| [MQTT](/docs/microservices/mqtt-adapter) | `toni-mqtt` | topic | MQTT v5 `response_topic` + `correlation_data` |
| [Kafka](/docs/microservices/kafka-adapter) | `toni-kafka` | topic | `toni-reply-to` / `toni-correlation-id` headers |

TCP and UDP are broker-less — the adapter is the server. The other five require the respective broker to be reachable from both sides.

All seven carry [streaming replies](/docs/microservices/rpc-controllers#streaming-replies) with the same frame grammar. What differs is how a caller says it has walked away: TCP and UDP send a cancel frame in-band on the call's own connection or socket, while the five broker transports publish the notice to a shared channel — `toni.rpc.cancel` on NATS, RabbitMQ and Kafka, `toni:rpc:cancel` on Redis, `toni/rpc/cancel` on MQTT — that every server instance listens to. Each transport page states its own.

Instead of binding their own socket, the TCP and UDP adapters can adopt one the caller already bound — `TcpAdapter::from_listener` / `UdpAdapter::from_socket` — for socket activation and zero-downtime restarts; see [Bind targets](/docs/techniques/bind-targets).
