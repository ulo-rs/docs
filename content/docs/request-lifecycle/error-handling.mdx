Ulo's error story has four layers, from most common to most specialized:

1. **Domain errors** — implement `ulo::Error` on your own types, return `Result<T, MyError>` from handlers, and the framework renders a canonical response with the right status on every transport.
2. **`HttpError`** — a convenience type for trivial cases that don't warrant a dedicated error.
3. **The error handler chain** — `#[catch(T)]` functions and `ErrorHandler` implementations that reshape specific errors into custom responses. The chain is the only error seam there is: handler errors and the framework's own events both travel it.
4. **Panic recovery** — `catch_unwind` around every pipeline segment, so a panic becomes a typed event on that same chain instead of tearing down the server.

## Domain errors with `ulo::Error`

The `ulo::Error` trait is `std::error::Error` plus the metadata the pipeline needs:

```rust
pub trait Error: std::error::Error + Send + Sync + 'static {
    /// Coarse classification — drives status codes and envelopes on every transport.
    fn kind(&self) -> ErrorKind;

    /// Human-readable message for the client. Defaults to `Display`.
    fn message(&self) -> Cow<'_, str> { /* ... */ }

    /// Structured payload merged into the response under `details`.
    fn details(&self) -> Option<serde_json::Value> { None }
}
```

Derive it with `#[derive(ulo::Error)]` and tag variants with `#[error_kind(KIND)]`:

```rust
#[derive(Debug, ulo::Error)]
enum UserError {
    #[error_kind(NotFound)]
    NotFound(String),

    #[error_kind(BadRequest)]
    InvalidId(String),

    #[error_kind(Conflict)]
    EmailTaken(String),
}

impl std::fmt::Display for UserError {
    fn fmt(&self, f: &mut std::fmt::Formatter<'_>) -> std::fmt::Result {
        match self {
            Self::NotFound(id) => write!(f, "user {id} not found"),
            Self::InvalidId(id) => write!(f, "invalid user id: {id}"),
            Self::EmailTaken(email) => write!(f, "email already in use: {email}"),
        }
    }
}

impl std::error::Error for UserError {}
```

The derive generates only the `kind()` impl — `Display` and `std::error::Error` stay yours (write them by hand or with `thiserror`). On an enum, a top-level `#[error_kind(...)]` is the default for untagged variants; without one, untagged variants fall back to `Internal`. Structs take a single top-level tag.

### ErrorKind

`ErrorKind` is the transport-independent vocabulary. Each transport maps it to its own wire form — the HTTP layer owns the status mapping:

| `ErrorKind` | HTTP status |
|---|---|
| `BadRequest` | 400 |
| `Unauthorized` | 401 |
| `Forbidden` | 403 |
| `NotFound` | 404 |
| `Conflict` | 409 |
| `UnprocessableEntity` | 422 |
| `TooManyRequests` | 429 |
| `Timeout` | 504 |
| `Unavailable` | 503 |
| `Unimplemented` | 501 |
| `Internal` | 500 |

The variant name (`"NotFound"`) is the stable `kind` identifier used in RPC and WebSocket envelopes.

## Returning errors from handlers

Handlers return `Result<T, MyError>`. A blanket `From<E: ulo::Error>` impl lifts the error into the transport's handler error type (`HttpError`, `RpcError`, `WsError`), so `?` works on any `ulo::Error`:

```rust
#[injectable]
pub struct UserService {}
impl UserService {
    fn find_user(&self, id: &str) -> Result<User, UserError> {
        if id == "1" {
            Ok(User { id: "1".into(), name: "John Doe".into() })
        } else {
            Err(UserError::NotFound(id.into()))
        }
    }
}

#[controller("/users")]
pub struct UserController {
    #[inject]
    service: UserService,
}

#[routes]
impl UserController {
    #[get("/{id}")]
    fn get_user(&self, Path(id): Path<String>) -> Result<Body, UserError> {
        let user = self.service.find_user(&id)?;
        Ok(Body::json(serde_json::to_value(user).unwrap()))
    }
}
```

`GET /users/999` renders the canonical HTTP envelope:

```json
{ "statusCode": 404, "message": "user 999 not found", "error": "Not Found" }
```

When `details()` returns `Some(value)`, it is merged into the body under a `details` key.

## HttpError

For one-off cases, `HttpError` skips the dedicated type:

```rust
use ulo::errors::HttpError;

#[get("/-/teapot")]
fn teapot(&self) -> Result<Body, HttpError> {
    Err(HttpError::custom(418, "I'm a teapot"))
}
```

| Constructor | Status |
|--------|--------|
| `HttpError::bad_request(msg)` | 400 |
| `HttpError::unauthorized(msg)` | 401 |
| `HttpError::forbidden(msg)` | 403 |
| `HttpError::not_found(msg)` | 404 |
| `HttpError::conflict(msg)` | 409 |
| `HttpError::unprocessable_entity(msg)` | 422 |
| `HttpError::internal_server_error(msg)` | 500 |
| `HttpError::custom(status, msg)` | any |

`HttpError` renders the same `{statusCode, message, error}` envelope via `to_response()`. It also implements `IntoResponse`, and carries an `AppError` variant that wraps lifted domain errors — `status_code()`, `message()`, and rendering all delegate to the wrapped error's `kind`/`message`/`details`.

## Custom rendering with `#[catch(T)]`

When the canonical envelope isn't enough — extra headers, a domain-specific body shape — a `#[catch(T)]` function claims errors of type `T` and produces the response directly:

```rust
use serde_json::json;
use ulo::{catch, Error, ErrorKind};
use ulo::context::HttpContext;
use ulo::HttpResponse;

#[derive(Debug)]
struct PaymentDeclined {
    reason_code: &'static str,
    retry_after_secs: u32,
}

impl std::fmt::Display for PaymentDeclined {
    fn fmt(&self, f: &mut std::fmt::Formatter<'_>) -> std::fmt::Result {
        write!(f, "payment declined ({})", self.reason_code)
    }
}
impl std::error::Error for PaymentDeclined {}
impl Error for PaymentDeclined {
    fn kind(&self) -> ErrorKind {
        ErrorKind::UnprocessableEntity
    }
}

#[catch(PaymentDeclined)]
async fn render_payment_declined(err: &PaymentDeclined, _ctx: &HttpContext) -> HttpResponse {
    HttpResponse::builder()
        .status(ulo::errors::http_status(err.kind()))
        .header("Retry-After", err.retry_after_secs.to_string())
        .json(json!({
            "type": "payment_declined",
            "reason_code": err.reason_code,
            "retry_after_secs": err.retry_after_secs,
        }))
        .build()
}
```

`#[catch(T)]` lowers a free `async fn (err: &T, ctx: &CtxType) -> ResponseType` into an `ErrorHandler` that downcasts the inbound error to `T` — non-matching errors fall through to the next handler. The function name becomes a unit struct. It is a value, not a provider, so attach it by instantiating it — `Name {}` — rather than by bare name, which asks the container for a token nothing registered:

```rust
#[controller("/billing")]
pub struct BillingController {}

#[routes]
#[use_error_handlers(render_payment_declined {})]
impl BillingController {
    #[post("/charge")]
    fn charge(&self) -> Result<Body, PaymentDeclined> {
        Err(PaymentDeclined { reason_code: "insufficient_funds", retry_after_secs: 60 })
    }
}
```

The context parameter picks the transport, and the return type follows from it: `&HttpContext` returning `HttpResponse` for HTTP, `&RpcContext` returning `RpcData` for RPC, `&WsContext` returning `WsMessage` for WebSocket, `&GrpcContext` returning `GrpcStatus` for gRPC. These are the bare answer types, not the `*HandlerResult` aliases an interceptor returns on the same transport.

## The ErrorHandler chain

`#[catch]` is sugar for the underlying trait:

```rust
use ulo::traits_helpers::{ChainError, ErrorHandler};

#[async_trait]
pub trait ErrorHandler<C: ?Sized + HandlerContext, R>: Send + Sync {
    async fn handle_error(&self, error: ChainError<'_>, ctx: &C) -> Option<R>;
}
```

`ChainError<'a>` is `&'a (dyn std::error::Error + Send + Sync + 'static)` — the chain owns the error and lends it to each handler in turn. Handlers downcast, then either claim the error (`Some(response)`) or fall through (`None`).

Implementing the trait directly suits handlers that match on more than one type:

```rust
use ulo::HttpResponse;
use ulo::context::HttpContext;
use ulo::errors::HttpError;

pub struct StatusPageErrorHandler;

#[async_trait]
impl ErrorHandler<HttpContext, HttpResponse> for StatusPageErrorHandler {
    async fn handle_error(&self, error: ChainError<'_>, _ctx: &HttpContext) -> Option<HttpResponse> {
        let http_error = error.downcast_ref::<HttpError>()?;
        if http_error.status_code() != 404 {
            return None; // pass to the next handler
        }
        Some(
            HttpResponse::builder()
                .status(404)
                .text("Nothing to see here.")
                .build(),
        )
    }
}
```

### Order and registration

Handlers are consulted most-specific first: **method → controller → global**. The first `Some` claims the error; if all return `None`, the transport's default rendering applies (the canonical envelope for `ulo::Error` / `HttpError` values, a 500 envelope for unknown errors).

- Method level: `#[use_error_handlers(...)]` on a handler
- Controller level: `#[use_error_handlers(...)]` on the `#[routes]` / `#[patterns]` / `#[subscriptions]` / `#[grpc_methods]` impl
- Global: per transport on the factory —

```rust
factory.use_global_http_error_handler(Arc::new(StatusPageErrorHandler));
// also: use_global_rpc_error_handler, use_global_ws_error_handler,
//       use_global_grpc_error_handler
```

The chain dispatches on handler-returned errors and framework events alike. For lifted domain errors, the chain sees the *underlying* error — `#[catch(UserError)]` matches a `UserError` returned through `?` even though the wire type wrapped it in `HttpError::AppError`.

<FromNest>
`#[catch(T)]` is the exception filter and `use_global_http_error_handler` is
`useGlobalFilters`, but the two sit at opposite ends of the workflow. In NestJS a
filter is where an error becomes a response, so most projects have one. In Ulo a
`#[derive(ulo::Error)]` type already renders itself through its `ErrorKind`, and
a handler is the override for the cases where that rendering is wrong.
</FromNest>

## Framework events

When the framework itself is the source of an error, it raises a typed event implementing `ulo::Error`. Events travel the error handler chain alongside handler errors, so `#[catch]` handlers reshape them the same way:

| Event | `kind` | Raised when | Transports |
|---|---|---|---|
| `GuardRejection` | `Forbidden` (403) | A guard returned `false`. Carries `guard_index` and an optional `reason`. | All four. A WebSocket *connect* is the exception: it refuses the upgrade instead of raising an event. |
| `Unrouted` | `NotFound` (404) | Nothing is registered to answer the call. Carries the `target` as the caller named it. | RPC and WebSocket. HTTP's 404 and gRPC's `Unimplemented` are written inside routing the framework does not own, so neither raises an event. |
| `MiddlewareFailure` | `Internal` (500) | Middleware returned `Err` before the handler ran. | HTTP, route-scoped middleware only. |
| `PanicRecovered` | `Internal` (500) | A panic was caught in the pipeline. Carries the `PipelineSegment` it happened in. | All four. |

All four are exported from `ulo::errors`; the crate root re-exports every one but `Unrouted`. Reshaping a guard rejection:

```rust
#[catch(ulo::errors::GuardRejection)]
async fn auth_failure(err: &ulo::errors::GuardRejection, _ctx: &HttpContext) -> HttpResponse {
    HttpResponse::builder()
        .status(ulo::errors::http_status(err.kind()))
        .json(json!({
            "error": "auth_required",
            "hint": "Send `x-auth-token: <token>`",
            "detail": err.message(),
        }))
        .build()
}
```

## Observing without shaping

A handler that returns `None` sees the error and changes nothing — the rendering below it runs exactly as it would have. That is how logging, metrics, and tracing attach to the pipeline. The chain stops at the first `Some`, so a decliner registered globally is consulted for every error no more specific handler claimed:

```rust
use std::sync::Arc;
use ulo::async_trait;
use ulo::context::HttpContext;
use ulo::traits_helpers::{ChainError, ErrorHandler};
use ulo::HttpResponse;

pub struct ErrorLogger;

#[async_trait]
impl ErrorHandler<HttpContext, HttpResponse> for ErrorLogger {
    async fn handle_error(&self, error: ChainError<'_>, ctx: &HttpContext) -> Option<HttpResponse> {
        tracing::error!(
            error = %error,
            path = %ctx.request().uri.path(),
            "request error",
        );
        None
    }
}
```

```rust
factory.use_global_http_error_handler(Arc::new(ErrorLogger));
```

### Reporting off the request path

A handler runs where the error happened: on the request path, with the client waiting. Enriching a report, shipping it to Sentry, writing it to a store and alerting on it are all slow, and none of them should hold a response open.

Publish the error onto a transport the app already speaks, and do the observing in a consumer. The publish is one socket write on the request path; everything after it happens in another process that can be slow, restarted, or scaled without the endpoint noticing.

```rust
use serde_json::json;
use ulo::RpcClient;

struct ErrorReporter {
    client: RpcClient,
}

#[async_trait]
impl ErrorHandler<HttpContext, HttpResponse> for ErrorReporter {
    async fn handle_error(&self, error: ChainError<'_>, ctx: &HttpContext) -> Option<HttpResponse> {
        let report = json!({
            "message": error.to_string(),
            "path": ctx.request().uri.path(),
            "method": ctx.request().method.as_str(),
        });

        // Telemetry does not get to decide whether the client gets an answer:
        // a broker that is down costs one failed write, logged and dropped.
        if let Err(e) = self.client.emit_json("errors.reported", &report).await {
            tracing::warn!(error = %e, "could not publish the error report");
        }

        None
    }
}
```

The consumer is an ordinary `#[event_pattern]` handler, and nothing waits on it:

```rust
use ulo::extractors::Payload;

#[controller]
pub struct ErrorConsumer {}

#[patterns]
impl ErrorConsumer {
    #[new]
    pub fn new() -> Self {
        Self {}
    }

    #[event_pattern("errors.reported")]
    async fn on_error_reported(
        &self,
        Payload(report): Payload<serde_json::Value>,
    ) -> Result<(), RpcError> {
        // ship, enrich, alert — this can take as long as it likes
        println!("{report}");
        Ok(())
    }
}
```

`examples/error_telemetry.rs` in the repository runs both halves in one process over RabbitMQ.

## Panic recovery

Every role a user writes — middleware, guards, interceptors, handlers, chain handlers, and response rendering — is wrapped in `catch_unwind` on every transport. A panic becomes a `PanicRecovered` event tagged with the segment it happened in, and the event is offered to the error handler chain. If nothing claims it, the transport renders `Internal`.

`PipelineSegment` names the site: `handler`, `guard`, `middleware`, `error_handler`, `response_rendering`, or `other`. Interceptors and middleware chain steps share the `middleware` segment, so an interceptor panic reads back under that name.

The recovery policy per segment:

- **Guard panic** — a bug, not a verdict. The event goes to the chain and, unclaimed, renders `Internal` on all four transports. A WebSocket *connect* is the exception: there is no answer to shape on a refused upgrade, so the connection closes with 1011 and no chain runs.
- **Interceptor panic** — the handler and the remaining inner steps are skipped; the event renders through the chain, tagged `middleware`.
- **Handler panic** — same path as a returned error, with `kind = Internal`.
- **Error handler panic** — that handler is skipped (`None`) and the chain continues, so one bad handler can't kill error recovery. The log line carries `chain_position`, counted from the most specific handler.
- **Renderer panic** — the fallback keeps the canonical envelope, written as a literal so none of the user code the renderer was calling runs again: `{"statusCode":500,"message":"Internal Server Error","error":"Internal Server Error"}` as `application/json` on HTTP, `{"status":"error","kind":"Internal","message":"Internal Server Error"}` on RPC and WebSocket.

### What gets logged

An event the chain can reach is delivered and narrated at `debug` — someone is being told, and the log line is for the operator watching. `tracing::error!` is reserved for what can reach nobody: a panicking `#[catch]` handler, a panicking renderer, and an unhandled error in the global middleware chain. An `error!` from the framework means a failure that nothing downstream could be told about.

## Other transports

The same model runs everywhere; only the wire shape differs:

- **RPC** — handlers return `Result<RpcData, RpcError>` or `Result<T, MyError>`; `RpcError::AppError` wraps lifted domain errors and renders `{"status": "error", "kind": "NotFound", "message": "..."}` as the reply payload. Chain handlers are `ErrorHandler<RpcContext, RpcData>`. A handler that answers with a sequence returns `RpcHandlerResult` instead, and an `Err` item ends the stream — see [RPC Controllers](/docs/microservices/rpc-controllers).
- **WebSocket** — `WsError::AppError` plays the same role; chain handlers are `ErrorHandler<WsContext, WsMessage>` and produce the message sent back to the client.
- **gRPC** — a `#[grpc_methods]` handler returns its own error implementing `ulo::Error`, or a `GrpcStatus` to name a code outside the eleven kinds. The error travels in `tonic::Status`'s source slot, so `#[catch(MyError)]` matches here as it does everywhere else. Chain handlers are `ErrorHandler<GrpcContext, GrpcStatus>` and can remap a status before it reaches the wire; gRPC registers per-method and per-service handlers via the same `#[use_error_handlers]` attribute on `#[grpc_methods]` impls.
