---
title: Attribute Markers
description: "NestJS-style #[body], #[param], and #[query] annotations on handler parameters."
---

Attribute markers annotate handler parameters directly — the NestJS-style `@Body()` / `@Param()` / `@Query()` shorthand. Instead of wrapping the parameter's type in an extractor, you mark it and receive the inner value:

```rust
#[post("/users")]
fn create_user(&self, #[body] dto: CreateUserDto) -> Body {
    Body::text(format!("Created user: {} <{}>", dto.name, dto.email))
}
```

Markers work in HTTP controllers only. The extraction markers are `#[body]`, `#[param]`, and `#[query]`; path-qualified spellings (`#[toni::body]`) work the same as the bare ones.

## `#[body]`

Delegates to the [`Body<T>` extractor](/docs/extractors/built-in#body--content-type-aware-body), so it is content-type-aware:

- `application/json` → JSON
- `application/x-www-form-urlencoded` → form decoding
- no `Content-Type` → tries JSON first, then form

```rust
#[derive(serde::Deserialize)]
struct CreateUserDto {
    name: String,
    email: String,
}

#[post("/users")]
fn create_user(&self, #[body] dto: CreateUserDto) -> Body {
    Body::text(format!("Created user: {} <{}>", dto.name, dto.email))
}
```

Unlike `Body(dto): Body<CreateUserDto>`, the marker binds the inner value — `dto` is a `CreateUserDto`, with no wrapper to destructure. A failed extraction returns a 400 with `{"error": "Failed to extract request body", "details": …}`.

## `#[query]`

Three modes, chosen by the parameter's type and whether the marker names a query parameter.

### Whole struct

`#[query]` with no argument deserializes the entire query string into the parameter's type, exactly like `Query<T>`:

```rust
#[derive(serde::Deserialize)]
struct SearchParams {
    q: String,
    limit: Option<usize>,
}

#[get("/advanced-search")]
fn advanced_search(&self, #[query] params: SearchParams) -> Body {
    let limit = params.limit.unwrap_or(10);
    Body::text(format!("Advanced search: '{}' (limit: {})", params.q, limit))
}
```

Failure returns a 400 with `{"error": "Failed to extract query parameters", "details": …}`.

### Named scalar

`#[query("name")]` reads that one query parameter and parses it with `str::parse`. This mode applies to scalar types: `String`, the integer and float types, `bool`, and `char`.

```rust
#[get("/search")]
fn search(
    &self,
    #[query("q")] query: String,
    #[query("limit")] limit: Option<usize>,
) -> Body {
    let limit = limit.unwrap_or(10);
    Body::text(format!("Searching for '{}' with limit {}", query, limit))
}
```

- Missing parameter → 400 with `{"error": "Missing required query parameter", "param": "q"}`
- Present but unparseable → 400 with `{"error": "Failed to parse query parameter", "param": "q", "details": …}`

`Option<T>` makes the parameter optional: missing → `None`. The sharp edge: a parameter that is present but unparseable still returns a 400, not `None` — `?limit=abc` for `Option<usize>` is an error, not an absent value.

The name belongs to this mode only. `#[query("filters")] f: FilterSet` — a name on a type that is not one of the scalars above — does not compile: it reports ``cannot find type `Query` in crate `::toni` ``, which names the generated path rather than the parameter that produced it. Drop the name and take the whole struct with `#[query]`, or take `Query<FilterSet>`.

### Defaults

`default` makes a named scalar infallible — a missing or unparseable value falls back to the default:

```rust
#[get("/products")]
fn list_products(
    &self,
    #[query("page", default = "1")] page: usize,
    #[query("pageSize", default = "20")] page_size: usize,
) -> Body {
    Body::text(format!("Products page {} (size: {})", page, page_size))
}
```

Three sharp edges:

- The default swallows unparseable values, not only missing ones — `?page=abc` yields `1`, never a 400.
- The default is a string literal parsed at request time, so a default that does not parse as the parameter's type panics on every request that falls back to it — not at compile time. The dispatcher catches the panic and offers it to the error chain as a `PanicRecovered`; unclaimed, the client gets a 500. The process survives, and the endpoint answers nothing else for as long as the literal is wrong.
- `default` and `Option<T>` are mutually exclusive. The fallback parses into the parameter's declared type, and `Option<usize>` has no `FromStr` impl, so `#[query("limit", default = "10")] limit: Option<usize>` fails to compile. Pick one: a default, or `None` for a missing value.

## `#[param]`

Reads one path parameter. The name argument is mandatory — `#[param]` without one is a compile error.

```rust
#[get("/users/{id}")]
fn get_user(&self, #[param("id")] user_id: i32) -> Body {
    Body::text(format!("User ID: {}", user_id))
}
```

The value is parsed with `str::parse`, so the type needs `FromStr` — not `Deserialize`.

- Missing parameter → 400 with `{"error": "Missing required path parameter", "param": "id"}`
- Parse failure → 400 with `{"error": "Failed to parse path parameter", "param": "id", "details": …}`

`default` is not supported on `#[param]` — the argument parses but has no effect.

<FromNest>
These are the closest thing Toni has to `@Param()`, `@Query()`, and `@Body()`,
and they carry gotchas the typed extractors do not. `#[param]` ignores a
`default`. A `#[query]` default that fails to parse panics when a request
arrives rather than at startup. A marker cannot share a signature with a typed
extractor. Prefer `Path<T>`, `Query<T>`, and `Json<T>` unless you specifically
want a marker's shape.
</FromNest>

## Mixing markers

Markers mix with each other:

```rust
#[post("/users/{id}")]
fn update_user(&self, #[param("id")] user_id: i32, #[body] dto: CreateUserDto) -> Body {
    Body::text(format!(
        "Updated user {}: {} <{}>",
        user_id, dto.name, dto.email
    ))
}
```

They do not mix with typed extractors. A handler is bound through one path or the other, whole: put a marker beside a `Json<T>`, a `Path<T>`, or a custom extractor and the non-marker parameter is never bound, which surfaces as an arity mismatch on the generated call —

```
error[E0061]: this method takes 2 arguments but 1 argument was supplied
```

— or, for a custom extractor, `cannot find value` naming the parameter. Neither diagnostic points at the mix. Spell the whole signature one way.

## Error shapes

Marker failures are inline 400 responses produced at the extraction site, bypassing the error-handler chain — the same delivery as [typed extractor failures](/docs/extractors/built-in#extraction-failures), but a different JSON shape. A typed extractor failure is always `{"error": "Extraction failed", "details": …}`; markers use per-marker messages (`"Failed to extract request body"`, `"Missing required query parameter"`, …) and name the offending parameter under `"param"` where one applies. A client, or a test, matching on one shape will miss the other in an app whose controllers are written both ways.

## One body, still

`#[body]` reads the request body through the same single-use channel as the typed body extractors, and it is counted the same way: the compile-time [one-body check](/docs/extractors/built-in) sees it as the `Body<T>` it extracts through. Two `#[body]` parameters, or a `#[body]` beside another body reader, are rejected before the crate builds, with both parameters named.

That check reads each parameter's type, so what it cannot see is a body read that never appears in the signature — a guard that consumed the body before the handler ran, or a custom extractor that calls `take_body` without declaring `CONSUMES`. Those fail at request time instead: the second reader gets a 400, and a `BodyAlreadyRead` error naming the extractor is logged at error level.
