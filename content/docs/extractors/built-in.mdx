---
title: Built-in Extractors
description: Type-safe request data extraction — path params, query strings, JSON body, raw bytes, streams, and validated inputs.
---

Extractors pull typed data out of the HTTP request. They appear as handler parameters, and every one of them is read through a single trait — [`FromContext`](/docs/extractors/custom) — against the handler's context.

Extractors come in two shapes:

- **Metadata extractors** borrow the request parts (headers, path params, query params, extensions) and leave the body alone. `Path`, `Query`, `Request`, and `Extensions` work this way. Any number of them can sit on one handler.
- **Body extractors** take the request body, which is single-use — it may be a stream. `Json`, `Body`, `Bytes`, `BodyStream`, `Multipart`, and `HttpRequest` work this way. Each declares `const CONSUMES: bool = true` on its `FromContext` impl.

**Only one body extractor may appear per handler.** The controller macro reads `CONSUMES` off each parameter's written type and rejects a second body reader at compile time, naming both offending parameters:

```
`dto` and `raw` both read the request body, and it can only be read once.
Keep one of them. If you need more than one view of the body, take `Bytes` (or `HttpRequest`) and parse it yourself.
```

Because the fact comes off the type rather than a list of names, an alias, an `Option`- or `Validated`-wrapped body extractor, a `#[body]` marker, and a [custom extractor](/docs/extractors/custom) that declares `CONSUMES` all count the same. What escapes the check is an extractor that calls `take_body` without declaring the const, and a guard that read the body before the handler ran — either way the second reader fails at request time with a `BodyAlreadyRead` error naming itself.

Attribute markers (`#[body]`, `#[param]`, `#[query]`) offer a NestJS-style shorthand over these extractors — see [Attribute Markers](/docs/extractors/markers).

## Path — route parameters

Extracts typed values from URL path segments. Scalars parse from the raw segment (`Path<i32>`, `Path<bool>`, `Path<String>`); structs deserialize with each field typed:

```rust
use ulo::extractors::Path;

// Single param
#[get("/{id}")]
fn find_one(&self, Path(id): Path<u32>) -> HttpResponse {
    // id parsed to u32 from the URL segment
}

// Multiple params via a struct
#[derive(serde::Deserialize)]
struct PostParams {
    user_id: u32,
    post_id: u32,
}

#[get("/{user_id}/posts/{post_id}")]
fn find_post(&self, Path(params): Path<PostParams>) -> HttpResponse {
    let user_id = params.user_id;
    let post_id = params.post_id;
    // ...
}
```

A segment that fails to parse (e.g. `abc` for `Path<i32>`) returns a 400 — see [Extraction failures](#extraction-failures).

<FromNest>
`@Param('id')` becomes a `Path<T>` parameter destructured in the handler
signature, and the route spells the parameter `{id}` — `:id` is a compile error.
The type is what parses: `Path<u32>` rejects a non-numeric segment before the
handler runs, so there is no `ParseIntPipe` to add.
</FromNest>

## Query — query string parameters

Deserializes the query string into a typed struct:

```rust
use ulo::extractors::Query;
use serde::Deserialize;

#[derive(Deserialize)]
struct SearchQuery {
    q: String,
    page: Option<u32>,
    limit: Option<u32>,
}

#[get("/search")]
fn search(&self, Query(params): Query<SearchQuery>) -> HttpResponse {
    let q = params.q;
    let page = params.page.unwrap_or(1);
    let limit = params.limit.unwrap_or(20);
    // ...
}
```

## Json — JSON body

Deserializes the request body as JSON. The `Content-Type` header is not checked — the bytes are parsed as JSON regardless. An empty body is an error, as is malformed JSON; both produce a 400. An empty body reports `Request body is not JSON`, which is the message for that one case and not a content-type complaint.

```rust
use ulo::extractors::Json;
use serde::Deserialize;

#[derive(Deserialize)]
struct CreateUserDto {
    name: String,
    email: String,
}

#[post("/")]
fn create(&self, Json(dto): Json<CreateUserDto>) -> HttpResponse {
    // dto is fully typed
}
```

## Body — content-type-aware body

Deserializes the body based on the `Content-Type` header:

- `application/json` → JSON
- `application/x-www-form-urlencoded` → form decoding
- no `Content-Type` → tries JSON first, then form
- any other content type → error (400)

```rust
use ulo::extractors::Body;

#[post("/")]
fn create(&self, Body(dto): Body<CreateUserDto>) -> HttpResponse {
    // works for both JSON and form-encoded bodies
}
```

Use `Json` when the endpoint only accepts JSON. Use `Body` when it also needs to support form submissions.

Two different types are spelled `Body`: `ulo::extractors::Body<T>` is this extractor, and `ulo::Body` is the response body a handler returns. A handler that takes one and returns the other needs an alias on one of the imports — `use ulo::Body as UloBody;` — or two `use` statements naming the same identifier collide.

## Bytes — raw binary data

Buffers the entire request body into a `Vec<u8>`:

```rust
use ulo::extractors::Bytes;

#[post("/upload")]
fn upload(&self, Bytes(data): Bytes) -> HttpResponse {
    let size = data.len();
    HttpResponse::ok()
        .json(serde_json::json!({ "received_bytes": size }))
        .build()
}
```

## BodyStream — unbuffered body stream

Yields the body as a raw stream of chunks, never loading it into memory at once. Use it for large uploads:

```rust
use futures::StreamExt;
use ulo::{Body, BodyStream};

#[post("/upload")]
async fn upload(&self, stream: BodyStream) -> Body {
    let mut total = 0usize;
    let mut s = Box::pin(stream.into_stream());
    while let Some(chunk) = s.next().await {
        total += chunk.unwrap().len();
    }
    Body::text(format!("received {total} bytes"))
}
```

`into_stream()` yields `Result<bytes::Bytes, _>` chunks. The stream it returns is not `Unpin`, so pin it — `Box::pin` above — before polling it with `next()`. `collect().await` buffers the whole body into a single `Bytes` and needs no pinning; reach for it when a code path turns out not to need streaming.

Extraction itself cannot fail on `BodyStream`'s own terms — its error type is `BodyExtractionError<Infallible>`, so the only possible failure is finding the body already read by another extractor.

`ulo-http-actix` and `ulo-http-rocket` hand the framework a body that is already buffered. `BodyStream` and `Multipart` still work there, with the bytes wrapped as a single-chunk stream — but nothing is incremental, and the memory is spent before the handler runs. Stream on `ulo-http-axum`, `ulo-http-salvo`, or `ulo-http-poem`.

## Multipart — form-data and file uploads

Parses `multipart/form-data` bodies field by field. See [Multipart / File Upload](/docs/extractors/multipart).

## HttpRequest — the whole request

A plain `HttpRequest` parameter hands the handler the full request (metadata plus body). It counts as the body consumer for that handler.

```rust
use ulo::HttpRequest;

#[post("/raw")]
async fn raw(&self, req: HttpRequest) -> HttpResponse {
    let (parts, body) = req.into_parts();
    // parts.headers, parts.uri, parts.method; body.collect().await for the bytes
}
```

## Request — request metadata without the body

A `Request` parameter is a read-only view of the request metadata: method, URI, headers, path params, query params, and extensions. It never touches the body, so it sits beside any body extractor, and extraction is infallible.

```rust
use ulo::Request;

#[get("/info")]
fn info(&self, req: Request) -> Body {
    let ua = req.header("user-agent").unwrap_or("unknown");
    Body::text(format!("{} {} from {}", req.method(), req.uri(), ua))
}
```

`Request` is also a built-in request-scoped provider — a controller can `#[inject]` it as a field instead of taking it per handler.

## Extensions — the per-message bag

`Extensions` is the typed key-value bag shared by everything handling the current message — a guard inserts a value, the handler reads it back by type. Extraction is infallible: a message with nothing attached yields an empty bag.

```rust
use ulo::context::Extensions;

#[get("/me")]
fn me(&self, ext: Extensions) -> Body {
    match ext.get::<AuthUser>() {
        Some(user) => Body::text(format!("Hello, {}", user.name)),
        None => Body::text("anonymous"),
    }
}
```

The bag is behind a lock, so `get::<T>()` returns a clone and needs `T: Clone + Send + Sync + 'static`. For a payload that cannot clone, `with::<T, _>(|v| …)` and `with_mut` run a closure against the value in place instead, holding the lock for the duration — don't reach back into the same bag from inside one.

Unlike the other extractors on this page, `Extensions` is not HTTP-specific — its one impl is generic over every handler context, so the same parameter means the same thing in a WebSocket or RPC handler.

## Option — optional extraction

Wrapping any extractor in `Option<T>` turns extraction failure into `None` instead of a 400 response:

```rust
#[get("/feed")]
fn feed(&self, user: Option<CurrentUser>) -> Body {
    match user {
        Some(CurrentUser(user)) => Body::text(format!("Welcome back, {}", user.name)),
        None => Body::text("Sign in for personalized content"),
    }
}
```

`CurrentUser` here is a [custom extractor](/docs/extractors/custom); `Option` wraps built-ins the same way. Several `Option`-wrapped extractors can coexist — useful for endpoints that accept JWT, API key, or anonymous access.

An `Option`-wrapped body extractor still reads the body, so it counts as the handler's body reader — `Option<Json<T>>` beside `Bytes` is rejected at compile time like any other pair.

## Validated — extraction + validation

Wraps an extractor and runs `validator` crate validation on the inner value before the handler sees it:

```rust
use ulo::extractors::{Json, Validated};
use serde::Deserialize;
use validator::Validate;

#[derive(Deserialize, Validate)]
struct CreateUserDto {
    #[validate(length(min = 2, max = 100))]
    name: String,

    #[validate(email)]
    email: String,

    #[validate(range(min = 13, max = 120))]
    age: u32,
}

#[post("/")]
fn create(&self, Validated(Json(dto)): Validated<Json<CreateUserDto>>) -> HttpResponse {
    // If any rule fails, the handler is never called.
    // dto.name is guaranteed 2-100 chars, dto.email a valid email, etc.
    HttpResponse::created()
        .json(serde_json::json!({ "name": dto.name }))
        .build()
}
```

`Validated` works with any extractor implementing `ValidatableExtractor` — provided for `Json`, `Path`, `Query`, `Body`, and `Payload`:

```rust
Validated<Json<Dto>>     // validate JSON body
Validated<Path<Dto>>     // validate path params
Validated<Query<Dto>>    // validate query params
Validated<Body<Dto>>     // validate content-type-aware body
Validated<Payload<Dto>>  // validate a WebSocket, RPC, or gRPC message
```

`Validated<E>` reads exactly what `E` reads. `Validated<Query<T>>` is a metadata extractor and leaves the body alone, so it can sit beside a body extractor on the same handler; `Validated<Json<T>>` counts as that handler's body reader:

```rust
#[post("/search")]
fn search(
    &self,
    Validated(Query(params)): Validated<Query<SearchQuery>>,
    Json(dto): Json<CreateUserDto>,
) -> Body {
    // the query is validated; Json still finds the body
    Body::text(format!("q={} name={}", params.q, dto.name))
}
```

A validation failure returns the same 400 shape as any other extraction failure, with the rule violations in `details`. To make a custom extractor validatable, see [Custom Extractors](/docs/extractors/custom#validation-support).

`Validated<E>` is generic over the context, not tied to HTTP: its impl reads `E: FromContext<C> + ValidatableExtractor` for any handler context `C`. `Validated<Payload<T>>` is therefore the same wrapper in a `#[subscribe_message]`, `#[message_pattern]`, or `#[grpc_method]` handler, validating the message the transport delivered:

```rust
use ulo::extractors::{Payload, Validated};
use ulo::{RpcData, RpcError};

#[message_pattern("users.create")]
async fn create_user(
    &self,
    Validated(Payload(dto)): Validated<Payload<CreateUserDto>>,
) -> Result<RpcData, RpcError> {
    // dto satisfied every #[validate] rule before this line
    Ok(RpcData::json(serde_json::json!({ "email": dto.email })))
}
```

Which inner extractors are available still depends on the transport — `Validated<Query<T>>` has no meaning off HTTP, and asking for it there is a trait-bound error.

## Extraction failures

<Callout type="info" title="Extraction failures bypass the error-handler chain">
When an extractor fails (and is not `Option`-wrapped), the handler never runs and the client receives an inline **400** response:

```json
{
  "error": "Extraction failed",
  "details": "Failed to deserialize JSON body: missing field `email` at line 1 column 15"
}
```
</Callout>

This response is produced directly at the extraction site — it does not pass through the error-handler chain.

## Multiple extractors

Any number of metadata extractors can combine with at most one body consumer:

```rust
#[derive(Deserialize)]
struct PaginationQuery {
    page: Option<u32>,
    per_page: Option<u32>,
}

#[put("/{id}")]
fn update(
    &self,
    Path(id): Path<u32>,
    Query(pagination): Query<PaginationQuery>,
    Validated(Json(dto)): Validated<Json<UpdateItemDto>>,
) -> HttpResponse {
    // Path and Query read metadata; Validated<Json<_>> consumes the body
}
```

## Custom extractors

Implement `FromContext` to create your own — a metadata extractor borrows `ctx.request()`; a body extractor calls `take_body` and declares `const CONSUMES: bool = true` so the one-body check covers it. See [Custom Extractors](/docs/extractors/custom).
