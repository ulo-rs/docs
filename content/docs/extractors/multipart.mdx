---
title: Multipart / File Upload
description: Handle multipart/form-data requests and file uploads with the Multipart extractor.
---

The `Multipart` extractor parses `multipart/form-data` request bodies. It yields fields one at a time — each field can be a plain text value or a file upload.

`Multipart` is a body-consuming extractor. Only one body-consuming extractor may appear per handler. Its extraction error is `BodyExtractionError<MultipartError>`, so a body already consumed by another extractor surfaces as the `AlreadyRead` variant rather than a `MultipartError`.

## Basic usage

```rust
use ulo::extractors::Multipart;

#[post("/upload")]
async fn upload(&self, mut mp: Multipart) -> impl IntoResponse {
    while let Some(field) = mp.next_field().await.unwrap() {
        let name = field.name().unwrap_or("unknown").to_string();
        let data = field.bytes().await.unwrap();
        println!("field={name} size={}", data.len());
    }
    HttpResponse::no_content().build()
}
```

## File upload example

```rust
use ulo::extractors::Multipart;

#[post("/upload")]
async fn upload(&self, mut mp: Multipart) -> Body {
    let mut file_name = String::from("unnamed");
    let mut description = String::new();

    while let Some(field) = mp.next_field().await.unwrap() {
        match field.name() {
            Some("description") => {
                description = field.text().await.unwrap_or_default();
            }
            Some("file") => {
                file_name = field
                    .file_name()
                    .unwrap_or("unnamed")
                    .to_string();
                let data = field.bytes().await.unwrap_or_default();
                // save data to disk or object storage
                println!("received {file_name}: {} bytes", data.len());
            }
            _ => {}
        }
    }

    Body::json(serde_json::json!({ "file": file_name, "description": description }))
}
```

Test with curl:

```bash
curl -X POST http://127.0.0.1:3000/upload \
     -F "description=my photo" \
     -F "file=@/path/to/photo.jpg"
```

## Field API

`next_field` yields `Result<Option<Field>, MultipartError>`. `Field` is `multer`'s, re-exported as `ulo::extractors::multipart::Field` — the module path, not `ulo::extractors::Field`. Naming it is only necessary to write a helper that takes one; the loop above never spells the type.

Each field exposes:

```rust
field.name() -> Option<&str>              // form field name
field.file_name() -> Option<&str>         // original filename (file fields only)
field.content_type() -> Option<&Mime>     // content-type of the field
field.text().await -> Result<String>      // read as UTF-8 text
field.bytes().await -> Result<Bytes>      // read as raw bytes
```

Fields must be consumed in order — calling `next_field` before fully reading the current field drops unread bytes.

## Error handling

`MultipartError` has two variants, and they are raised at different moments:

```rust
pub enum MultipartError {
    MissingBoundary,   // Content-Type header is absent or has no boundary parameter
    Parse(multer::Error),
}
```

`MissingBoundary` is raised during extraction, before the handler runs, so a request that was not sent as `multipart/form-data` never reaches your code. The client gets the standard inline 400:

```json
{
  "error": "Extraction failed",
  "details": "missing multipart boundary in Content-Type"
}
```

`Parse` is the only variant `next_field` can yield — a body that announced a boundary and then did not follow it. Handle it per field. Unwrapping it panics the handler, which the dispatcher renders as a 500; returning it as an `HttpError` gives the client the 400 the truncated upload deserves:

```rust
use ulo::{extractors::Multipart, HttpError};

#[post("/upload")]
async fn upload(&self, mut mp: Multipart) -> Result<Body, HttpError> {
    while let Some(field) = mp.next_field().await
        .map_err(|e| HttpError::BadRequest(e.to_string()))?
    {
        // process field
    }
    Ok(Body::json(serde_json::json!({ "ok": true })))
}
```

## Size and buffering

The framework imposes no limit on an upload's size — the adapter decides. `ulo-http-rocket` caps a request at 32 MiB; `ulo-http-salvo` imposes no cap of its own. Enforce your own budget by counting bytes as you read fields, and reject past the threshold rather than after the allocation.

On `ulo-http-actix` and `ulo-http-rocket` the whole body is buffered before `Multipart` sees it, so field-by-field reading there costs the memory up front. Incremental reads need `ulo-http-axum`, `ulo-http-salvo`, or `ulo-http-poem`.
