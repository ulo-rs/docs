---
title: Configuration Validation
description: Validate configuration values at startup using the validator crate.
---

Configuration validation catches bad environment values before the server starts accepting requests. `ulo-config` integrates with the `validator` crate — the presence of `#[validate(...)]` attributes on your config fields is the opt-in. There is no Cargo feature to enable; a config without `#[validate]` attributes never references the `validator` crate.

## Setup

```toml title="Cargo.toml"
[dependencies]
ulo-config = "0.1"
validator = { version = "0.20", features = ["derive"] }
```

## Annotating configuration

Derive `Validate` alongside `Config` and add `#[validate(...)]` constraints:

```rust
use ulo_config::Config;
use validator::Validate;

#[derive(Config, Validate, Clone)]
pub struct AppConfig {
    #[env("APP_PORT")]
    #[default(8080u16)]
    #[validate(range(min = 1024, max = 65535))]
    pub port: u16,

    #[env("WORKER_THREADS")]
    #[default(4u16)]
    #[validate(range(min = 1, max = 64))]
    pub worker_threads: u16,

    #[env("DATABASE_URL")]
    #[validate(url)]
    pub database_url: String,

    #[env("JWT_SECRET")]
    #[validate(length(min = 32))]
    pub jwt_secret: String,
}
```

The generated `Validate` impl delegates to `validator::Validate::validate`, so every constraint the `validator` crate supports works here — `range`, `url`, `length`, `email`, `custom`, and the rest.

## When validation runs

Validation runs inside the `ConfigModule` constructors, after every field has been read and parsed, before the application starts:

- `ConfigModule::<AppConfig>::from_env()` / `from_file(path)` / `from_env_file(env)` return `Err(ConfigError::ValidationError(...))` when a constraint fails.
- `ConfigModule::<AppConfig>::new()` panics, with a message naming the config type; an embedding process or a test can catch the unwind.

Loading and validating are one step — there is no separate `load_and_validate()` call.

## Failure behavior

A failing constraint prevents the module from being constructed, and the application never starts with an invalid configuration:

```rust
use ulo_config::{Config, ConfigModule};

fn main() {
    match ConfigModule::<AppConfig>::from_env() {
        Ok(module) => {
            let cfg = module.get_ref();
            println!("config valid: port={}", cfg.port);
        }
        Err(e) => {
            eprintln!("config rejected: {e}");
            std::process::exit(1);
        }
    }
}
```

```
APP_PORT=80 cargo run
config rejected: Validation failed: ...
```

The error is a `ConfigError::ValidationError` wrapping the `validator` crate's error display, which names the offending field and the failed rule.

## Custom validators

Use `validator`'s custom validation support for constraints beyond the built-in ones:

```rust
use validator::ValidationError;

fn validate_database_url(url: &str) -> Result<(), ValidationError> {
    if !url.starts_with("postgresql://") && !url.starts_with("postgres://") {
        return Err(ValidationError::new("must be a PostgreSQL URL"));
    }
    Ok(())
}

#[derive(Config, Validate, Clone)]
pub struct AppConfig {
    #[env("DATABASE_URL")]
    #[validate(custom(function = "validate_database_url"))]
    pub database_url: String,
}
```
