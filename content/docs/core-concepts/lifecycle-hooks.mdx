---
title: Lifecycle Hooks
description: Run code at specific points in the application and module lifecycle — initialization, startup, and shutdown.
---

Lifecycle hooks are methods on providers, controllers, and modules that Toni calls at specific points during application startup and shutdown. They're declared with attribute macros inside `impl` blocks. All hooks are `async fn` taking `&self`; the two startup hooks return `toni::InitResult`, and returning `Err` aborts startup. The two fail from different phases: an `on_module_init` failure surfaces as `Err(StartupError::HookFailed)` from `ToniFactory::create`, an `on_application_bootstrap` failure from `bind()`.

<Callout type="warn">
Hooks fire only on **singleton** providers. Request- and transient-scoped instances do not exist at application init or shutdown, so there is no firing point for one. Declared on such a provider a hook compiles and is never called — the only signal is a `dead_code` warning on the method.
</Callout>

## Available hooks

### `#[on_module_init]`

`async fn(&self) -> toni::InitResult`. Runs after the DI container is fully initialized, before the application starts accepting requests. Use it for setup that requires dependencies to be ready.

```rust
#[injectable]
pub struct DatabaseService {
    name: String,
}
impl DatabaseService {
    #[new]
    pub fn new() -> Self {
        Self { name: "PostgreSQL".to_string() }
    }

    #[on_module_init]
    async fn connect(&self) -> toni::InitResult {
        println!("connecting to {}", self.name);
        // establish connections, warm caches...
        Ok(())
    }
}
```

### `#[on_application_bootstrap]`

`async fn(&self) -> toni::InitResult`. Runs after all modules have initialized (all `on_module_init` hooks complete), the last hook before the server accepts connections.

```rust
#[on_application_bootstrap]
async fn on_ready(&self) -> toni::InitResult {
    println!("ready to serve requests");
    Ok(())
}
```

### `#[on_module_destroy]`

`async fn(&self)`. Runs first during shutdown. Use it to release module resources.

```rust
#[on_module_destroy]
async fn cleanup(&self) {
    println!("closing connections");
}
```

### `#[before_application_shutdown]`

`async fn(&self, signal: Option<String>)`. Runs after `on_module_destroy`. `signal` is the OS signal name that triggered shutdown, if any (e.g. `"SIGTERM"`) — the parameter can be omitted from the signature if unused.

```rust
#[before_application_shutdown]
async fn prepare_shutdown(&self, signal: Option<String>) {
    println!("stop accepting work (signal: {:?})", signal);
}
```

### `#[on_application_shutdown]`

`async fn(&self, signal: Option<String>)`. The final hook in the shutdown sequence. Same optional `signal` parameter.

```rust
#[on_application_shutdown]
async fn finalize(&self, _signal: Option<String>) {
    println!("final cleanup complete");
}
```

## Execution order

### Startup
```
1. Providers instantiated (constructors run in dependency order)
2. on_module_init            — module-level hooks first, then provider-level
3. on_application_bootstrap  — module-level hooks first, then provider-level
4. Adapters start accepting connections
```

### Shutdown
```
1. on_module_destroy               — release module resources
2. before_application_shutdown(signal) — stop accepting work
3. on_application_shutdown(signal) — final cleanup
```

Within each phase, module-level hooks run before provider-level hooks.

## Full example

```rust
#[injectable]
pub struct CacheService {
    connected: std::sync::atomic::AtomicBool,
}

impl CacheService {
    #[new]
    pub fn new() -> Self {
        Self { connected: std::sync::atomic::AtomicBool::new(false) }
    }

    #[on_module_init]
    async fn connect(&self) -> toni::InitResult {
        println!("cache: connecting...");
        self.connected.store(true, std::sync::atomic::Ordering::SeqCst);
        Ok(())
    }

    #[on_application_bootstrap]
    async fn warm_up(&self) -> toni::InitResult {
        println!("cache: warming up hot keys");
        Ok(())
    }

    #[before_application_shutdown]
    async fn drain(&self, signal: Option<String>) {
        println!("cache: stopping writes (signal: {:?})", signal);
    }

    #[on_application_shutdown]
    async fn disconnect(&self) {
        println!("cache: connection closed");
    }
}
```

## Hooks on modules

Modules take the same hooks with the same shapes. Use the `#[module]` attribute on an `impl` block instead of a struct:

```rust
#[module(providers: [CacheService])]
impl CacheModule {
    #[on_module_init]
    async fn init(&self) -> toni::InitResult {
        println!("CacheModule initialized");
        Ok(())
    }

    #[on_module_destroy]
    async fn destroy(&self) {
        println!("CacheModule destroyed");
    }
}
```

Controllers accept the same hooks inside their impl blocks. On a request-scoped controller, the init and bootstrap hooks fire on each per-call instance rather than once at startup, and their `Err` is discarded — a failed init does not stop the call. The three shutdown hooks do not fire on a per-call target at all; they run only on a singleton one, which is the only instance still alive when the application shuts down.

## Triggering shutdown

<Callout type="warn" title="Nothing runs these hooks unless you wire a signal">
Toni installs no SIGTERM/SIGINT handlers. Wire signals to a `ShutdownHandle`:

```rust
let mut app = ToniFactory::new().create_with(AppModule).await?;
app.use_http_adapter(AxumAdapter::new(), ("127.0.0.1", 3000))?;
app.bind().await?;

let shutdown = app.shutdown_handle();
tokio::spawn(async move {
    tokio::signal::ctrl_c().await.expect("failed to listen for Ctrl+C");
    shutdown.shutdown();
});

app.run().await; // drains in-flight requests, then runs the shutdown hooks
```
</Callout>

`ShutdownHandle::shutdown()` lets in-flight requests drain before hooks run. `app.close().await` runs the hooks and closes adapters immediately — it returns `()`, so there is nothing to `?` or `.unwrap()`.

<FromNest>
NestJS starts running these on SIGTERM once `enableShutdownHooks()` is called.
Toni installs no signal handlers at all. Nothing triggers the shutdown hooks on
Ctrl-C unless you wire a signal to a `ShutdownHandle` yourself.
</FromNest>

## Standalone context

`ToniFactory::create_application_context` (for CLI tools, workers) runs the same startup hooks, including bootstrap — a failing bootstrap hook propagates as `Err(StartupError::HookFailed)` from it, since a standalone context has no `bind()` to fail from. Call `close()` to trigger the shutdown sequence:

```rust
let mut ctx = ToniFactory::new()
    .create_application_context_with(AppModule)
    .await?;

let service = ctx.get::<UserService>().await?;
// do work...

ctx.close().await; // on_module_destroy → before_application_shutdown → on_application_shutdown
```
