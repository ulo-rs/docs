A **provider** is anything the DI container manages: a service struct, a configuration value, a database connection, a factory-created object. The most common form is a **service** — a struct that holds business logic and can be injected into controllers and other services.

## Defining a service

```rust
use ulo::injectable;

#[injectable]
pub struct UsersService {
    // owned state — not injected
    #[default(1000)]
    max_users: u32,
}

impl UsersService {
    pub fn find_all(&self) -> Vec<String> {
        vec!["Alice".into(), "Bob".into()]
    }

    pub fn find_one(&self, id: u32) -> Option<String> {
        if id == 1 { Some("Alice".into()) } else { None }
    }
}
```

`#[injectable]` goes directly on the struct; the `impl` block is standard Rust. `#[default(expr)]` initializes owned state; untagged fields fall back to `Default::default()`. The macro supplies the `Clone` impl the container needs — every injection site binds an owned clone, never a shared reference.

`#[controller]` does not derive `Clone`, because a dispatch target is not a provider: the framework builds it and calls it, and nothing resolves it by type. Naming one as a dependency therefore fails at the field:

```
error[E0277]: the trait bound `UsersController: Clone` is not satisfied
19 | #[injectable]
   | ------------- in this attribute macro expansion
22 |     ctrl: UsersController,
   |     ^^^^^^^^^^^^^^^^^^^^^ the trait `Clone` is not implemented for `UsersController`
   = note: this error originates in the derive macro `Clone` which comes from the expansion of
           the attribute macro `injectable`
help: consider annotating `UsersController` with `#[derive(Clone)]`
```

<Callout type="warn" title="Do not take that help">
Deriving `Clone` on the controller silences the error and leaves the dependency unresolvable — the container has no entry under the controller's type. Inject the service the controller injects instead, and let both sites share it.
</Callout>

## Injecting into other services

Mark dependency fields with `#[inject]`. The container resolves them and fills the fields directly — no constructor required:

```rust
#[injectable]
pub struct OrdersService {
    #[inject]
    users_service: UsersService,
    #[inject]
    payments_service: PaymentsService,
}

impl OrdersService {
    pub fn create_order(&self, user_id: u32, amount: f64) -> String {
        let user = self.users_service.find_one(user_id)
            .expect("user not found");
        self.payments_service.charge(&user, amount);
        format!("Order created for {user}")
    }
}
```

For `OrdersService` to inject `UsersService` and `PaymentsService`, those services must be available in the same module scope — either directly in `providers` or from an imported module's `exports`.

## Constructor injection with `#[new]`

Field injection covers the common case. When construction needs logic — or a dependency is consumed without being stored — tag a constructor with `#[new]`:

```rust
#[injectable]
pub struct Banner {
    prefix: String,
}

impl Banner {
    #[new]
    fn new(config: Config) -> Self {
        // config is injected, used, and NOT stored as a field
        Self { prefix: format!("<{}>", config.env()) }
    }
}
```

Each `#[new]` parameter is resolved from the container by type (or by token with `#[inject("TOKEN")]` on the parameter). A bare `new()` without the attribute is not picked up as a DI constructor.

<FromNest>
`#[injectable]` replaces `@Injectable()`, but there is no constructor to inject
into. Dependencies are `#[inject]` fields on the struct, and ordinary methods
stay in a plain `impl` block. Use `#[new]` only when construction has to run
code — a bare `new()` is not detected.
</FromNest>

## Registering in a module

```rust
#[module(
    imports: [PaymentsModule],             // PaymentsService comes from here
    controllers: [OrdersController],
    providers: [OrdersService, UsersService],
)]
pub struct OrdersModule;
```

## Async initialization

Use the `#[on_module_init]` lifecycle hook to run async setup after the service is constructed but before the application starts accepting requests. Startup hooks are `async fn` returning `ulo::InitResult`; returning `Err` aborts startup:

```rust
#[injectable]
pub struct DatabaseService {
    #[default("PostgreSQL".to_string())]
    name: String,
}

impl DatabaseService {
    #[on_module_init]
    async fn connect(&self) -> ulo::InitResult {
        // runs once, after all providers in this module are instantiated
        println!("Connecting to {}", self.name);
        Ok(())
    }

    pub async fn query(&self, sql: &str) { /* ... */ }
}
```

See [Lifecycle Hooks](/docs/core-concepts/lifecycle-hooks) for the full sequence and the shutdown-side hooks.

## Provider scope

Providers are singletons by default — one instance per module scope. `#[injectable(scope = "...")]` accepts three values:

```rust
#[injectable]                          // singleton (default): one shared instance
#[injectable(scope = "request")]       // one instance per execution
#[injectable(scope = "transient")]     // fresh instance per resolution
```

<Callout type="info" title="Request scope means one execution">
An execution is one HTTP request, one WebSocket message, one RPC or gRPC call, or one standalone execution built with `ProviderContext::standalone()`. Within an execution the instance is shared by clone — one construction, cloned into every injection site — so mutable state that must be visible across sites belongs behind an `Arc<Mutex<_>>`. A lifecycle hook declared on a request- or transient-scoped provider is never called: the framework has no firing point for one, and the only signal is a `dead_code` warning on the hook method. Put hooks on a singleton.
</Callout>

A singleton dispatch target — an HTTP controller, an RPC controller, or a gRPC service — that depends on a request-scoped provider is elevated to request scope automatically, and a warning is logged when it happens. Declaring `#[controller(scope = "request")]` states the intent and silences the warning. See [Provider Patterns](/docs/core-concepts/provider-patterns) for value providers, factory providers, alias providers, and custom token providers.

## Implementing enhancer traits

An enhancer is a provider that implements the role trait — the trait impl *is* the declaration. There are no marker attributes: declare `#[injectable]`, implement `Guard<HttpContext>` (or `Interceptor`, `ErrorHandler`, `Middleware`), register in `providers`, and apply with `#[use_guards]`. `Interceptor` and `ErrorHandler` also carry the transport's answer type — `Interceptor<HttpContext, HttpResponse>` for HTTP:

```rust
use ulo::{async_trait, injectable, context::HttpContext, traits_helpers::Guard};

#[injectable]
pub struct AdminGuard {
    #[inject]
    auth_service: AuthService,
}

#[async_trait]
impl Guard<HttpContext> for AdminGuard {
    async fn can_activate(&self, ctx: &HttpContext) -> bool {
        ctx.request().headers.get("authorization")
            .and_then(|h| h.to_str().ok())
            .and_then(|h| h.strip_prefix("Bearer "))
            .map(|t| self.auth_service.verify(t))
            .unwrap_or(false)
    }
}
```

Register it in the module's `providers`, then apply it by type name — the type-name form resolves the instance (with its injected dependencies) from the DI container:

```rust
#[module(
    controllers: [ProtectedController],
    providers: [AdminGuard, AuthService],
)]
pub struct ProtectedModule;
```

```rust
#[routes]
#[use_guards(AdminGuard)]
impl ProtectedController { /* ... */ }
```

The context type in the trait names the transport: `Guard<HttpContext>` guards HTTP routes, `Guard<WsContext>` guards WebSocket messages, `Guard<RpcContext>` guards RPC patterns. See [Guards](/docs/request-lifecycle/guards).
