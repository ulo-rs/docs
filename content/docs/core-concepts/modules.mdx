Modules are the primary organizational unit in Ulo. Each module is a struct annotated with `#[module]` that declares:

- **`controllers`** — the dispatch targets owned by this module: HTTP controllers, RPC controllers, gRPC services
- **`providers`** — the services and values managed by this module's DI scope
- **`imports`** — other modules whose exported providers this module needs
- **`exports`** — the providers this module makes available to importing modules

## Basic module

```rust
use ulo::module;

#[module(
    controllers: [UsersController],
    providers: [UsersService],
)]
pub struct UsersModule;
```

The `#[module]` macro transforms this struct into a full module definition. You don't write methods on the struct — the macro generates everything needed for the DI scanner.

`controllers:` takes every dispatch target, not only HTTP. All three are `#[controller]` structs; the handler impl names the transport — `#[routes]` for HTTP, `#[patterns]` for RPC, `#[grpc_methods(proto::Trait)]` for gRPC. WebSocket gateways stay in `providers:`.

```rust
#[module(
    controllers: [UsersController, UsersRpcController, UsersGrpcService],
    providers: [UsersService, ChatGateway],
)]
pub struct UsersModule;
```

A `#[controller]` with no handler impl is valid; it dispatches nothing.

## Imports and exports

Modules can import providers from other modules. The exporting module must explicitly list what it shares.

```rust title="database/database_module.rs"
#[module(
    providers: [DatabaseService],
    exports: [DatabaseService],   // available to any module that imports DatabaseModule
)]
pub struct DatabaseModule;

// users/users_module.rs
#[module(
    imports: [DatabaseModule],    // DatabaseService is now injectable here
    controllers: [UsersController],
    providers: [UsersService],    // UsersService can #[inject] DatabaseService
)]
pub struct UsersModule;
```

`exports` lists providers from this module's `providers` by type name. Only exported providers are visible outside the module; everything else is private to that module's scope.

`controllers:` and `exports:` take a bare name, not a path: `exports: [inner::Svc]` fails to parse with ``error: expected `,` `` at the first `::`. `use` the type and list its name. `providers:` does take a path, and also takes the provider macros.

## The module tree

Every application has a root module. `UloFactory::create` starts scanning from there, recursively resolving the full module graph.

```rust title="app_module.rs"
#[module(
    imports: [
        DatabaseModule,
        UsersModule,
        AuthModule,
    ],
)]
pub struct AppModule;

// main.rs
#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let mut app = UloFactory::create(AppModule).await?;
    app.use_http_adapter(AxumAdapter::new(), ("127.0.0.1", 3000))?;
    app.start().await?;
    Ok(())
}
```

The root module itself typically has no controllers or providers — it composes feature modules.

`create` accepts any module — a `#[module]` struct or a `DynamicModule` — so a worker that only needs one integration can pass `SeaOrmModule::for_root(url)` directly as the root.

## Global modules

Marking a module `global: true` makes its exports available to every module in the tree without importing it:

```rust title="infrastructure/infrastructure_module.rs"
#[module(
    global: true,
    providers: [LoggerService, ConfigService, MetricsService],
    exports: [LoggerService, ConfigService, MetricsService],
)]
pub struct InfrastructureModule;

// app_module.rs — imported once, at the root
#[module(
    imports: [InfrastructureModule, UsersModule, AuthModule],
)]
pub struct AppModule;
```

Every module in the application can now inject `LoggerService`, `ConfigService`, or `MetricsService` without listing `InfrastructureModule` in its own `imports`. Reserve this for cross-cutting infrastructure — explicit imports keep dependencies visible.

## Lifecycle hooks on modules

Attach lifecycle callbacks directly to the module by switching from `pub struct` to `impl` and declaring the hooks inside that block. Module hooks share the provider hook shape — `async fn`, with startup hooks returning `ulo::InitResult` — and run before the provider hooks of the same phase:

```rust
#[module(
    providers: [DatabaseService],
    exports: [DatabaseService],
)]
impl DatabaseModule {
    #[on_module_init]
    async fn init(&self) -> ulo::InitResult {
        println!("DatabaseModule initialized");
        Ok(())
    }
}
```

See [Lifecycle Hooks](/docs/core-concepts/lifecycle-hooks) for the full sequence.

## Module-scoped middleware

The `impl` form also accepts a `configure_middleware` method for applying middleware to route patterns:

```rust
use ulo::traits_helpers::MiddlewareConsumer;

#[module(controllers: [UsersController], providers: [RequestTrackingMiddleware])]
impl UsersModule {
    fn configure_middleware(&self, consumer: &mut MiddlewareConsumer) {
        consumer
            .apply(LoggerMiddleware::new())
            .for_routes(vec!["/users/*"]);

        // DI-resolved middleware (constructor dependencies injected)
        consumer
            .apply_token::<RequestTrackingMiddleware>()
            .exclude(vec!["/users/public/*"])
            .for_routes(vec!["/users/*"]);
    }
}
```

See [Middleware](/docs/request-lifecycle/middleware) for route patterns and the `Middleware` trait.

## Dynamic modules

For cases where a module's configuration depends on runtime values (connection strings, API keys, feature flags), a function builds the module at runtime and the call goes directly in `imports`:

```rust
#[module(
    imports: [
        SeaOrmModule::for_root("postgres://localhost/mydb"),
        UsersModule,
    ],
)]
pub struct AppModule;
```

`DynamicModule` is a first-class framework type: a module whose providers and exports are determined at runtime rather than compile time. All integration crates (`ulo-db-seaorm`, `ulo-db-redis`, …) implement their `for_root` functions with it, and you can build your own:

```rust
use ulo::DynamicModule;

pub struct FeatureFlagsModule;

impl FeatureFlagsModule {
    pub fn for_root(api_key: &str) -> DynamicModule {
        DynamicModule::builder("FeatureFlagsModule")
            .provider(FeatureFlagsClientFactory::new(api_key))
            .export::<FeatureFlagsClient>()
            .build()
    }
}
```

The builder's `export::<T>()` exports by type, `export_token("NAME")` exports a string-token provider, and `global()` marks the module global.

### Identity and deduplication

A dynamic module's identity is its builder name plus the configuration of its providers. Importing the same module twice — say two feature modules each list `SeaOrmModule::for_root("postgres://localhost/app")` — registers it once; the second import dedups.

An identity renders as `base` on its own, or `base#<16 hex digits>` once configuration is folded in. That rendered key is the module's public address: the registry token, the `Display` string, the name in the scan log and in a clash refusal, and the argument [`get_module_by_id`](/docs/core-concepts/dependency-injection#scoping-a-lookup-to-one-module) takes. For a `#[module]` struct the base is the fully-qualified type path; for a `DynamicModule` it is the string the builder was given.

Two calls with **different** configuration are different modules. If both export the same token (two unnamed `for_root` calls of one integration), startup is refused with an error naming both modules; one would shadow the other and nothing would report it. Integrations expose named constructors (`for_root_named`) for this; a custom multi-instance module opts into the same identity machinery by implementing `identity_hint()` on its `ProviderFactory`, returning a string that distinguishes one configuration from another.

## Implementing `ModuleMetadata` by hand

`#[module]` and `DynamicModule` both produce a `ModuleMetadata` implementation. Writing one directly is the third option, and the one to reach for when a module has to answer differently depending on what it was constructed with — a different identity, a different provider set, a conditional export.

The trait is five required methods plus defaulted ones:

```rust
use ulo::ModuleIdentity;
use ulo::traits_helpers::{ControllerFactory, ModuleMetadata, ProviderFactory};

pub struct MetricsModule {
    endpoint: String,
}

impl MetricsModule {
    pub fn for_root(endpoint: impl Into<String>) -> Self {
        Self { endpoint: endpoint.into() }
    }
}

impl ModuleMetadata for MetricsModule {
    fn identity(&self) -> ModuleIdentity {
        // Two endpoints are two modules; the same endpoint imported twice dedups.
        ModuleIdentity::named("MetricsModule").fingerprinted(&self.endpoint)
    }

    fn is_global(&self) -> bool {
        true
    }

    fn imports(&self) -> Option<Vec<Box<dyn ModuleMetadata>>> {
        None
    }

    fn controllers(&self) -> Option<Vec<Box<dyn ControllerFactory>>> {
        None
    }

    fn providers(&self) -> Option<Vec<Box<dyn ProviderFactory>>> {
        Some(vec![Box::new(MetricsSinkFactory::new(&self.endpoint))])
    }

    fn exports(&self) -> Option<Vec<String>> {
        Some(vec![ulo::di::token_of::<MetricsSink>()])
    }
}
```

Import it like any other module — the expression in `imports:` is the module value itself:

```rust
#[module(imports: [MetricsModule::for_root("http://collector:4317"), UsersModule])]
pub struct AppModule;
```

Two details are easy to get wrong. Exports are **tokens**, not types, so build them with `token_of::<T>()` rather than formatting a name by hand — that is the function registration uses, and the two sides agree only because they share it. And the trait is declared `#[async_trait(?Send)]` for the sake of its lifecycle hooks: a plain `impl` is enough while you override none of them, and the attribute goes on the impl block the moment you override one.

`ModuleIdentity::named` is for a module identified by a string. A module identified by its own type uses `ModuleIdentity::of_type::<Self>()`, which derives the base from `token_of::<Self>()`; `.fingerprinted(&config)` then folds configuration into either form.

The providers a module hands back are `ProviderFactory` values — see [writing a provider factory by hand](/docs/core-concepts/provider-patterns#writing-a-provider-by-hand).
