CORS for HTTP and WebSockets work differently at the protocol level — Toni handles them as two separate concerns.

## HTTP CORS

The built-in `CorsMiddleware` registers on the global chain — no extra dependencies:

```rust
use std::sync::Arc;
use toni::ToniFactory;
use toni::middleware::CorsMiddleware;
use toni_axum::AxumAdapter;

#[tokio::main]
async fn main() {
    let mut factory = ToniFactory::new();
    factory.use_global_middleware(Arc::new(CorsMiddleware::permissive()));

    let mut app = factory.create_with(AppModule).await.unwrap();
    app.use_http_adapter(AxumAdapter::new(), ("127.0.0.1", 3000)).unwrap();
    app.start().await.unwrap();
}
```

Global middleware runs before routing, so preflight `OPTIONS` requests are answered directly with `204 No Content` — including for routes that define no `OPTIONS` handler. The middleware behaves identically on all five HTTP adapters.

### Fine-grained configuration

`CorsMiddleware::permissive()` is useful in development. For production, restrict origins, methods, and headers with `CorsOptions`:

```rust
use toni::middleware::{AllowedOrigins, CorsMiddleware, CorsOptions};

let cors = CorsMiddleware::new(CorsOptions {
    origins: AllowedOrigins::List(vec![
        "https://myapp.com".into(),
        "https://staging.myapp.com".into(),
    ]),
    methods: vec!["GET".into(), "POST".into(), "PUT".into(), "DELETE".into()],
    allowed_headers: Some(vec!["authorization".into(), "content-type".into()]),
    credentials: true,
    ..CorsOptions::default()
});

factory.use_global_middleware(Arc::new(cors));
```

Behavior worth knowing:

- Origins in `AllowedOrigins::List` match exactly, scheme and port included.
- `allowed_headers: None` (the default) reflects the request's `Access-Control-Request-Headers`.
- `credentials: true` echoes the specific origin instead of `*` — the spec forbids combining the two.
- A request without an `Origin` header passes through untouched. A disallowed origin is not rejected server-side; the response carries no CORS headers and the browser enforces the block.
- Remaining fields: `exposed_headers: Vec<String>` and `max_age: Option<u64>` (seconds). Defaults: any origin, `GET`/`HEAD`/`PUT`/`PATCH`/`POST`/`DELETE`, no credentials.

### tower-http alternative

`tower_http::cors::CorsLayer` still works through the `tower-compat` feature (`TowerLayer::new(CorsLayer::permissive())`) when you need behavior the built-in doesn't cover, such as `allow_private_network`. See [Middleware](/docs/request-lifecycle/middleware#tower-layers).

## WebSocket origin validation

WebSockets do not use CORS. There is no preflight — the browser upgrades the connection directly and sends an `Origin` header in the handshake. The server decides whether to accept or reject based on that header. `Access-Control-*` response headers are not checked by the browser for WebSocket connections.

The right place to validate the `Origin` header in Toni is a **guard** on the gateway. Gateway-level guards run after the handshake and before `on_connect` fires. There is no HTTP status left to refuse with by then, so a refusal is delivered as frames: the client receives the canonical `{status, kind, message}` envelope, then a close frame.

A guard's `false` closes with 1008 (policy violation), the code RFC 6455 reserves for a rule the caller broke — it has none for authentication. An `on_connect` that returns `Err` picks its code from the error's kind: 1013 for `TooManyRequests`, 1008 for the other client-fault kinds, 1011 for anything else. `WsError::Refused { code, reason }` names a code directly and sends the close alone, with no envelope in front of it — that is how a protocol with a refusal code of its own, such as graphql-ws's 4406, is answered.

A guard is an `#[injectable]` struct implementing `Guard<WsContext>`. The handshake headers live on the client as a plain `HashMap<String, String>` (header names lowercase):

```rust
use toni::async_trait;
use toni::context::WsContext;
use toni::traits_helpers::Guard;
use toni::injectable;

#[injectable]
pub struct OriginGuard;

#[async_trait]
impl Guard<WsContext> for OriginGuard {
    async fn can_activate(&self, ctx: &WsContext) -> bool {
        ctx.client()
            .handshake
            .headers
            .get("origin")
            .map(|origin| origin == "https://myapp.com")
            .unwrap_or(false)
    }
}
```

The connection's session already exists while the guard runs, so a guard that derives something worth keeping — the validated origin, a tenant — can stash it with `ctx.session().insert(...)` for every later message to read.

Apply it with `#[use_guards]` on the gateway's `#[subscriptions]` impl, and register both in the module:

```rust
use toni::websocket::{WsClient, WsHandlerOutput, WsHandlerResult, WsMessage};
use toni::{module, subscriptions, websocket_gateway};

#[websocket_gateway("/chat")]
pub struct ChatGateway;

#[subscriptions]
#[use_guards(OriginGuard)]
impl ChatGateway {
    #[subscribe_message("message")]
    async fn on_message(&self, _client: WsClient, _msg: WsMessage) -> WsHandlerResult {
        Ok(WsHandlerOutput::Empty)
    }
}

#[module(providers: [ChatGateway, OriginGuard])]
pub struct AppModule;
```

A connection rejected by the guard closes before `on_connect` fires.

### Multiple allowed origins from config

Guards resolve through DI, so an origin allowlist can come from configuration:

```rust
use toni::async_trait;
use toni::context::WsContext;
use toni::traits_helpers::Guard;
use toni_config::ConfigService;
use toni::injectable;

#[injectable]
pub struct OriginGuard {
    #[inject]
    config: ConfigService<AppConfig>,
}

#[async_trait]
impl Guard<WsContext> for OriginGuard {
    async fn can_activate(&self, ctx: &WsContext) -> bool {
        let allowed = &self.config.get_ref().allowed_origins;
        ctx.client()
            .handshake
            .headers
            .get("origin")
            .map(|origin| allowed.iter().any(|a| a == origin))
            .unwrap_or(false)
    }
}
```

### Missing Origin header

Browsers always send `Origin` for cross-origin WebSocket connections. Direct connections (e.g., `curl`, native apps, or same-origin pages) may omit it. The examples above default to `false` (reject) on a missing header — the safer default for public-facing gateways.

## Why they're separate

| | HTTP CORS | WebSocket origin |
|---|---|---|
| Protocol mechanism | `Access-Control-*` headers | `Origin` header in HTTP upgrade |
| Browser enforcement | Strong — blocks request before it's sent | Minimal — browser sends but doesn't block |
| Preflight | Yes (`OPTIONS`) | No |
| Where to handle | Global middleware (`CorsMiddleware`) | `Guard<WsContext>` on the gateway |
